- (direction) User requested a spec for Super Admin Tenant Onboarding: a SystemUser creates a new Tenant, first AuthAccount + TenantUser admin, assigns Tenant Admin role, provisions the tenant's Postgres schema, and rolls back/audits on failure.
- (decision) Mode: express distillation. Input is concise but sufficient; unresolved operational choices are captured as assumptions and open questions instead of blocking.
- (decision) Slug: super-admin-tenant-onboarding. Artifact path: _bmad-output/specs/spec-super-admin-tenant-onboarding/.
- (decision) Adopted companion: _bmad-output/brainstorming/brainstorm-core-auth-3-tier-rbac-review-2026-08-17/brainstorm-intent.md because it records the AuthAccount/SystemUser/TenantUser split and RBAC constraints that this onboarding spec must preserve.
- (capability) CAP-1: A permitted SystemUser can submit one tenant-onboarding request containing tenant identity data and first-admin identity data; success: authorized system-token request creates a tracked onboarding attempt and unauthorized tenant/non-system/missing-permission requests fail before any tenant state is created.
- (capability) CAP-2: The system creates the new Tenant in a non-active provisioning state; success: the Tenant slug/name are persisted only once for the request and are not usable for tenant login or tenant-scoped routes until the full onboarding completes.
- (capability) CAP-3: The system creates the first admin login identity and actor for the new tenant; success: exactly one AuthAccount and one TenantUser are associated with the new tenant admin, with service-layer actor-scope rules preserved.
- (capability) CAP-4: The system ensures a tenant-scoped Tenant Admin role and assigns it to the first TenantUser; success: the role belongs to the new tenant, carries only TENANT-scope permissions, and the first admin receives that role before activation.
- (capability) CAP-5: The system provisions the new tenant's Postgres schema and required tenant-schema bootstrap objects; success: the schema is resolvable through the existing tenancy layer and all required bootstrap migrations complete before tenant activation.
- (capability) CAP-6: The onboarding workflow compensates or marks failed state when any step errors; success: no failed attempt leaves an active Tenant, usable first-admin login, dangling role assignment, or untracked tenant schema without a corresponding failure audit entry.
- (capability) CAP-7: Every onboarding attempt is audited with actor, request identity, per-step outcomes, rollback/compensation outcome, and final status; success: success and failure paths both produce immutable audit evidence without storing plaintext credentials.
- (capability) CAP-8: Repeating the same onboarding request is idempotent by a caller-supplied request key or deterministic uniqueness checks; success: a retry after timeout returns the existing completed/failed attempt outcome instead of creating duplicate tenant/account/schema records.
- (constraint) Only SystemUser actors with an explicit SYSTEM-scope tenant-onboarding permission may run this flow; no isSuperAdmin bypass is allowed because this codebase's SystemUser still goes through Role->Permission checks.
- (constraint) AuthAccount/SystemUser/TenantUser actor scoping remains intact: the first admin AuthAccount backs a TenantUser, not a SystemUser, and the flow must not create an AuthAccount that backs both actor types.
- (constraint) Tenant Admin role assignment must be tenant-scoped: Role.tenantId equals the new Tenant id and a tenant role cannot receive SYSTEM-scope permissions.
- (constraint) Tenant schema provisioning must use the existing tenancy/schema-resolution layer and validated schema names; no raw schema-name concatenation path may be introduced.
- (constraint) Audit records are never rolled back or deleted as compensation; failed attempts must retain enough evidence for support and manual cleanup.
- (constraint) Tenant activation is the commit point exposed to the product: downstream tenant login/routes must treat pre-activation/provisioning/failed tenants as unavailable.
- (decision) Rollback and failure semantics are large enough to live in spec-authored companion failure-modes.md instead of bloating the kernel.
- (assumption) Assumed tenant onboarding is a backend/API capability first; a Super Admin UI can be added later but is not required by this SPEC.
- (assumption) Assumed tenant schema provisioning belongs in the same logical onboarding workflow even if implementation uses separate Prisma and Knex/Postgres operations under compensation rather than one shared database transaction.
- (question) Open question: What exact SYSTEM permission code authorizes tenant onboarding, e.g. tenants.create or system.tenants.onboard?
- (question) Open question: What is the canonical Tenant Admin role name/code and initial permission set for a new tenant?
- (question) Open question: Does the first admin AuthAccount receive an initial password, an invite/setup token, or another credential bootstrap path?
- (question) Open question: Where should onboarding audit records live (new Prisma model/table, LogEntry extension, or dedicated audit table), and what retention policy applies?
- (question) Open question: What tenant schema naming convention is canonical for newly provisioned tenants if the existing tenancy layer has more than one candidate derivation?
- (assumption) Assumed Tenant will have an activation gate capable of representing provisioning/active/failed, but this SPEC does not pin whether that is a Tenant.status column, separate onboarding table state, or another equivalent mechanism.
- (question) Open question: What exact Tenant activation-state representation should be implemented (Tenant.status enum, separate onboarding state table, or equivalent gate)?
