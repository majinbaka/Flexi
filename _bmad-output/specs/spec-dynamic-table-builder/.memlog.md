- (decision) Storage model: Runtime Physical DDL — real Postgres tables/columns per tenant-defined table/field, built via the existing tenant-schema Knex layer (TenantKnexService/resolveTenantSchema from spec-schema-per-tenant-core.md). User confirmed over JSONB-hybrid and EAV alternatives surfaced in research. Reason: matches the Knex infra already built specifically 'for the future dynamic-tables data path'.
- (decision) Scope includes basic relations: linked-record fields between dynamic tables within the same tenant. User confirmed over deferring relations to a later spec.
- (capability) CAP-1: Tenant admin can define a dynamic table (name + initial field set) via API; success: table + column creation compiles to real physical DDL in the tenant's Postgres schema, wrapped in one transaction with the Flexi metadata row describing it.
- (capability) CAP-2: Tenant admin can add/remove/modify fields (columns) on an existing dynamic table; success: additive changes (ADD COLUMN with constant DEFAULT) apply without a table rewrite; destructive/type-changing edits follow an expand/contract flow (new column, dual-write period, backfill, cutover) rather than an in-place unsafe ALTER.
- (capability) CAP-3: Field definitions support a validation ruleset (required, type constraints, string length, numeric range, enum) enforced at the application layer (DTO validation) on every dynamic-table write; success: an invalid write against a table's field rules is rejected with a field-level error before touching the DB.
- (capability) CAP-4: Tenant admin can define a linked-record (relation) field on a dynamic table pointing at another dynamic table in the same tenant; success: relation reads return joined/aggregated data via server-side json_agg (no N+1), and cross-tenant linking is rejected.
- (capability) CAP-5: Every DDL-issuing operation (create table, add/alter/drop column) runs through a migration engine that records the change and can be replayed/audited; success: each dynamic-table structural change is captured as a migration record scoped to the tenant's schema, consistent with the deferred cross-tenant migration tooling's withSchema()-per-file pattern.
- (capability) CAP-6: Runtime DDL statements are executed safely under concurrent load; success: every DDL statement sets a bounded lock_timeout before executing and runs off the request/response path (async queue), so a blocked ALTER fails fast instead of cascading a lock-queue stall onto live reads/writes.
- (capability) CAP-7: Tenant admin can create/edit tables and fields through a frontend UI (not just raw API calls); success: a form-driven table/field builder in the frontend app calls the module's API and reflects live validation errors from CAP-3.
- (constraint) All dynamic-table DDL and DML must go through Knex via TenantKnexService.forCurrentTenant()/resolveTenantSchema() from the existing tenancy layer — never a new Prisma dynamic-model workaround, never raw string-concatenated SQL. Reason: this is the exact reason that layer was built; reusing it keeps schema-name injection defense (resolveTenantSchema's allowlist) as the single choke point.
- (constraint) Every dynamic table gets tenant_id-free design (the table already lives inside the tenant's own Postgres schema, so no row-level tenant_id column is needed on dynamic tables themselves) but every index still leads appropriately for the table's own query patterns (e.g. (created_at) for pagination) since cross-tenant scans are impossible by construction (separate schema).
- (constraint) Guardrail ceilings (max tables/tenant, max columns/table, row limits, rate limits) must be re-derived from Flexi's own expected tenant profile before being hardcoded, per research's explicit caveat that the source report's numeric figures (100k rows, 100 cols, etc.) are untraceable illustrative guesses, not benchmarked facts. This spec records the guardrail *capability* (CAP-8) but treats exact numbers as an open question, not a frozen constant.
- (capability) CAP-8: The module enforces per-tenant guardrails (max dynamic tables per tenant schema, max columns per table) to bound system-catalog growth; success: creation requests beyond the configured ceiling are rejected with a clear error, and the ceiling is a ConfigService-backed value, not a hardcoded literal.
- (constraint) statement_timeout and lock_timeout for DDL sessions must be explicit, configured values (ConfigService/env), following this codebase's existing pattern of surfacing tunables in env.validation.ts rather than hardcoding them (mirrors the still-open deferred item on TenantKnexService pool bounds).
- (constraint) Non-goal: tenant schema provisioning (creating a new tenant's Postgres schema) is out of scope — deferred separately, this module assumes a tenant's schema already exists when its admin starts defining dynamic tables.
- (decision) Non-goal: cross-tenant migration replay tooling (a migrateAllTenants() runner across all tenant schemas) is out of scope — already tracked as a separate deferred-work item (schema-per-tenant-implementation-guide §6); this module only needs its own migrations to be schema-scoped and replayable per-tenant, not a fleet-wide runner.
- (decision) Non-goal: advanced field types beyond basic scalars + relations (e.g. computed/formula fields, file/attachment fields, lookup/rollup aggregations across relations) are out of scope for this spec's first cut — flagged as a natural follow-up, not a gap in this spec.
- (decision) Non-goal: fleet-wide catalog-object-budget metric/alerting (cross-tenant monitoring of total Postgres catalog growth) stays deferred per deferred-work.md — this spec's CAP-8 only covers per-tenant enforcement, not fleet observability.
- (question) Open question: exact numeric guardrail values (max tables/tenant, max columns/table, row/page/rate limits) are unresolved — research's source figures are untraceable illustrative guesses. Needs Flexi's own tenant-profile assumptions before CAP-8 gets concrete defaults; recommend resolving in bmad-architecture or via a follow-up decision before bmad-build implements CAP-8's ceiling values.
- (question) Open question: relation field cardinality (one-to-many vs many-to-many, and whether many-to-many needs an implicit join table) is not yet specified for CAP-4 — needs a decision before implementation; defaulting assumption is one-to-many + many-to-one only for the first cut, many-to-many deferred, but this is not yet user-confirmed.
- (assumption) Assumed CAP-6's async DDL queue uses the codebase's existing infra choices rather than introducing a new dependency; research suggested BullMQ (Redis-backed) but this codebase has no Redis/BullMQ today — flagged as an open question for architecture, not decided here.
- (decision) CAP-6's async DDL queue is backed by Redis + BullMQ, newly introduced as a dependency for this module. User confirmed adding this infra over staying synchronous or deferring the decision — matches research's explicit recommendation. Supersedes the earlier 'assumption' entry flagging this as unresolved.
- (constraint) Redis + BullMQ are new backend dependencies introduced by this module specifically for the DDL job queue; env config (e.g. REDIS_URL) must follow the existing env.validation.ts pattern (required, validated) rather than being ad hoc.
