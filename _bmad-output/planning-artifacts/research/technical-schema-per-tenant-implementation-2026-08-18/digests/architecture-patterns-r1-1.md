# Digest: Schema-per-Tenant Implementation — Architecture Patterns in Practice

Research round: R1 · Dimension: Architecture patterns in practice
Accessed: 2026-08-18

## Claims

1. **Claim:** In a NestJS + Knex + PostgreSQL schema-separated multi-tenancy implementation, query-level schema scoping is done with Knex's `.withSchema(tenantId)` (e.g. `getPool()("identity").withSchema(tenantId).where("id", id).first()`), and the author explicitly rejected using `SET search_path` because their implementation approach would have required per-tenant DB users/connections, which they judged would exhaust Postgres `max_connections` ("too many clients already") and break shared connection-pool efficiency.
   Source: "Multi-Tenancy (Schema separated) with NestJS, Knex and PostgreSQL in SAP BTP" — Nicola Zanon, inextenso.dev
   URL: https://www.inextenso.dev/multi-tenancy-schema-separated-with-nestjs-knex-and-postgresql-in-sap-btp
   pub_date: 2022-10-01 · accessed: 2026-08-18 · confidence: medium (single production write-up on this exact stack; the search_path-requires-per-tenant-users reasoning is this author's specific setup, not a general Postgres/Knex constraint — search_path can normally be set per-session/per-transaction without separate DB roles) · class: patterns

2. **Claim:** Same source: tenant resolution is done via a NestJS `AsyncContextInterceptor` that extracts tenant ID from the request and stores it in Node's `AsyncLocalStorage`, explicitly to avoid REQUEST-scoped provider performance penalties ("unfortunate performance implications" of factory providers with REQUEST scope forcing dependent services into request scope). Health-check endpoints are skipped from tenant extraction. Uses a **single shared connection pool** (min 2, max 50+) across all tenants rather than per-tenant pools; PgBouncer is mentioned as a possible mitigation for scale but left untested.
   Source: same as above (inextenso.dev, Nicola Zanon)
   pub_date: 2022-10-01 · accessed: 2026-08-18 · confidence: medium · class: patterns

3. **Claim:** Knex's official docs confirm `withSchema()` works on the **query builder** (select/insert/update/delete), not just the schema builder (createTable/dropTable/alterTable): `knex.withSchema('public').select('*').from('users')` generates `select * from "public"."users"`. Docs state schema specification via `withSchema()` is recommended over dot-notation in identifier strings (`schemaName.tableName`), since the latter "may render queries incorrectly."
   Source: Knex.js official documentation, Query Builder guide
   URL: https://knexjs.org/guide/query-builder.html
   pub_date: undated (current docs site) · accessed: 2026-08-18 · confidence: high (primary/official source) · class: versions/compatibility

4. **Claim:** A known historical Knex bug (#3034): `migrate.latest({ schemaName })` ignored the `schemaName` option and ran migrations against the knexfile's default schema instead of the dynamically specified one, causing "table already exists" failures when trying to provision isolated schemas programmatically. Reported against Knex 0.16.3 in Feb 2019, later closed. A community package `knex-migration-with-schema` exists specifically to work around the gap ("no simple way to run migrations across different schemas programmatically, sending the schema name as a parameter to knex.migrate()").
   Source: GitHub knex/knex Issue #3034; npm package knex-migration-with-schema
   URL: https://github.com/knex/knex/issues/3034 ; https://www.npmjs.com/package/knex-migration-with-schema
   pub_date: 2019-02-05 (issue), package undated · accessed: 2026-08-18 · confidence: low-medium — **flag: this is a 2019-era report against Knex 0.16.3; current Knex is in the 3.x line, and it's unconfirmed whether current versions still have this exact limitation or whether the closure represents a real fix.** class: versions/compatibility (stale — needs re-verification against current Knex version before relying on it)

5. **Claim (provisioning pattern, general):** Common tenant-provisioning pattern is: create the tenant's schema (`CREATE SCHEMA tenant_xxx`), then run the application's migration set against that new schema — i.e. "migrate fresh" rather than clone-from-template in the tooling surveyed. One npm package explicitly splits this into two functions: one to create the schema, one to execute migrations against it.
   Source: npm package knex-migration-with-schema (description); corroborated generally by DEV Community "Multi-Tenant Architecture" overview
   URL: https://www.npmjs.com/package/knex-migration-with-schema
   pub_date: undated · accessed: 2026-08-18 · confidence: low — **gap: no primary source found that documents a "clone template schema" (e.g. `CREATE SCHEMA ... LIKE` / `pg_dump`-and-restore-into-new-schema) technique as a *recommended* production pattern; only passing mentions were found (see Gaps below).** class: patterns

6. **Claim:** Under transaction-mode connection poolers (e.g. PgBouncer) with schema-per-tenant, if tenant identity is established via session-scoped mechanisms (`SET SESSION`, session-level `current_setting`), the connection returned to the pool after a transaction can retain that session state, and the next tenant to check out that pooled connection can silently inherit the previous tenant's identity/schema context — a cross-tenant leakage risk. The recommended mitigation is to make tenant-identity-setting transaction-scoped: `set_config('app.current_tenant_id', tenant, true)` with `is_local = true`, so the setting is cleared the instant the transaction commits/rolls back.
   Source: "How to architect multi-tenant SaaS on Postgres" — Manveer Chawla, ClickHouse Engineering blog
   URL: https://clickhouse.com/resources/engineering/multi-tenant-saas-postgres-architecture
   pub_date: 2026-05-25 · accessed: 2026-08-18 · confidence: high (recent, named author, concrete mechanism cited) · class: patterns

7. **Claim:** Same ClickHouse source explicitly frames schema-per-tenant as risky/overhead-heavy at scale: "the heavy overhead of the connection pool and the extreme complexity of executing N-schema migrations outweigh the perceived isolation gains," citing schema-drift management across many schemas and pg_catalog bloat growing linearly with schema count, and states "schema-per-tenant is rarely the right pick for a new SaaS application in 2026."
   Source: same as claim 6 (ClickHouse, Manveer Chawla)
   pub_date: 2026-05-25 · accessed: 2026-08-18 · confidence: high · class: landscape — **note: this is an anti-recommendation on the already-decided architecture choice, out of scope for "how to implement," but directly informs which pitfalls (pooling, catalog bloat, migration fan-out) to design around.**

8. **Claim:** A second, independent source makes the same core point about schema-per-tenant scaling limits: with hundreds of tenant schemas, Postgres system catalogs "grow into millions of rows," which "slows the query planner as it consults the catalog on every query," and the approach "likely won't scale beyond a few hundred tenants." Also states cross-tenant queries require "complex cross-schema joins" and migrations "need to be applied to each tenant's schema," increasing migration complexity. Provisioning is described generically as "creating the schemas" then each tenant "gets identical tables" (migration-based), and querying at runtime is via "the app sets the search path per request," with the caveat that "there is no database-level enforcement of preventing access to the wrong schema" — isolation depends on application-layer correctness, not a DB guarantee.
   Source: "Approaches to tenancy in Postgres" — Simeon Griggs, PlanetScale blog
   URL: https://planetscale.com/blog/approaches-to-tenancy-in-postgres
   pub_date: 2026-04-21 · accessed: 2026-08-18 · confidence: high (independent corroboration of catalog-bloat and no-DB-level-enforcement points from claim 6/7) · class: landscape

9. **Claim:** NestJS request-scoped (`REQUEST` scope) providers are documented/discussed in the community as carrying real performance costs because they force any class that depends on them to also become request-scoped, generating new instances per request; `AsyncLocalStorage` (directly, or via the `nestjs-cls` library which wraps it for NestJS DI) is presented as the preferred alternative for propagating per-request tenant context without incurring that scope penalty. A typical flow: Auth Guard verifies JWT to Tenant Resolver extracts tenantId to stores it in AsyncLocalStorage to downstream services/repositories read it to scope queries.
   Source: aggregated from search snippets citing nestjs-cls docs and community posts (fabian.ski "Multi Tenancy with NestJS async-hooks"; dev.to/nestjs-ninja NestJS TypeORM and Multi-Tenancy; oneuptime.com Node.js multi-tenancy guide) — **not independently fetched/verified this round, snippet-level only**
   pub_date: mixed/unconfirmed · accessed: 2026-08-18 · confidence: low-medium (not fetched directly; corroborated in spirit by claim 2 from the fetched inextenso source) · class: patterns

10. **Claim:** A named production-pitfalls write-up on multi-tenant NestJS lists concrete leak vectors relevant to schema-per-tenant-adjacent implementations: (a) lookup endpoints that skip tenant scoping (`findUnique({ where: { id } })` returning another tenant's record when only `id` is used, not `tenantId + id`); (b) cache-key collisions when cache keys aren't tenant-namespaced (e.g. key `settings` shared across tenants); (c) background/queue jobs running without tenant context in the payload; (d) admin endpoints reusing standard service methods/routing that assume request-scoped tenant context, risking bleed. Recommended fixes: enforce tenant context via AsyncLocalStorage, derive tenant ID only from verified JWT claims (never request body), composite-key all lookups, tenant-namespace cache keys and job payloads, add DB-level guardrails (composite unique keys, RLS), and write cross-tenant-access regression tests.
   Source: "Multi-Tenant NestJS: Stop Leaks Before They Start" — Thinking Loop, Medium
   URL: https://medium.com/@ThinkingLoop/multi-tenant-nestjs-stop-leaks-before-they-start-15361ca576ab
   pub_date: 2026-02-07 · accessed: 2026-08-18 · confidence: medium (recent, concrete examples, but single-author blog, not deeply schema-per-tenant-specific — pitfalls apply more generally across multi-tenant patterns) · class: patterns

11. **Claim:** PostgreSQL's `search_path` is a session variable that determines default unqualified-table-name resolution order; there is a known attack class called "search_path hijacking" where, if `search_path` isn't validated/pinned, an attacker (or buggy code path) can manipulate it to redirect unqualified-table-name queries to an unintended/malicious schema.
   Source: "search_path Hijacking: The PostgreSQL Attack You've Never Heard Of" — dev.to/ofri-peretz
   URL: https://dev.to/ofri-peretz/searchpath-hijacking-the-postgresql-attack-youve-never-heard-of-10co
   pub_date: not captured this round (snippet only, not fetched) · accessed: 2026-08-18 · confidence: low (snippet-level, not verified against full article; needs a direct fetch to confirm mechanism, whether it applies to `withSchema`-style fully-qualified queries too, and any Postgres-version-specific mitigation like `search_path` pinning via `ALTER ROLE ... SET search_path`) · class: patterns — **flagged for follow-up fetch**

12. **Claim (tangential/low-relevance — included for completeness, not central to schema-per-tenant):** A documented Knex.js SQL-injection issue affects `.where()` value-handling (object/array values passed as query values, exploiting quoted-identifier behavior), reportedly present as of Knex 2.3.0 at time of writing, tracing back to an original 2016 report; the article claims no confirmed fix at time of publication. This is about **value injection in `.where()`**, not about dynamic schema-name/identifier injection in `withSchema()` — **no source found this round substantiates an injection risk specific to passing a dynamic tenant schema name into `withSchema()` or `knex.raw` schema-qualified queries.** Knex's official Raw guide does document `??` / `:name:` identifier-binding syntax as the safe way to parameterize identifiers (schema/table names) when raw SQL is unavoidable.
   Source: "6 Year Old SQL Injection Vulnerability in Knex.js" — ghostccamm.com; Knex.js official Raw guide (knexjs.org/guide/raw)
   URL: https://www.ghostccamm.com/blog/knex_sqli/ ; https://knexjs.org/guide/raw
   pub_date: 2022-11-24 (ghostccamm post) · accessed: 2026-08-18 · confidence: low for relevance to this dimension (general Knex value-injection issue, not schema-identifier-specific; also 4 years old, current-version fix status unconfirmed) / high for the `??`/`:name:` identifier-binding syntax itself (official docs) · class: versions/compatibility — **flag: age >1 month bar for version claims not met; do not cite the "still vulnerable" claim as current without re-checking against latest Knex release notes.**

## Leads (for follow-up rounds)

- **Contradiction/tension:** The two most recent and best-sourced 2026 write-ups found (ClickHouse, PlanetScale) both argue schema-per-tenant is generally not recommended for new builds at current scale expectations (catalog bloat, migration fan-out, no DB-level enforcement) — while the one hands-on NestJS+Knex+Postgres implementation write-up found (inextenso, 2022) implements it successfully in production for SAP BTP. Worth flagging to the requester even though the row-level-vs-schema decision is stated as already made: the implementation-quality bar (pooling strategy, migration tooling, catalog growth monitoring) matters more given these are known failure modes, not hypothetical ones.
- **Open sub-question:** No primary source was found describing a "clone a template schema" provisioning technique (e.g., `CREATE SCHEMA foo; SELECT clone_schema('template', 'foo')` via a plpgsql helper function, or `pg_dump --schema=template | sed | psql`) as used in a real Node/Knex production system. Only "migrate fresh into new schema" was substantiated. If the target platform wants template-cloning specifically, it needs a dedicated follow-up search (e.g., "postgres clone_schema function plpgsql", "pg_dump single schema restore new schema name sed").
- **Open sub-question:** Whether Knex's `migrate.latest({schemaName})` limitation (GitHub #3034, reported against 0.16.3 in 2019) is still present in current Knex (3.x line) was not verified — needs a direct check against current Knex changelog/issues or a fresh reproduction.
- **Open sub-question:** The `dev.to/ofri-peretz` "search_path hijacking" post was found only as a search snippet, not fetched directly — worth a full fetch to confirm whether it's relevant to a `withSchema()`-based (fully-qualified) implementation, which should be largely immune since it doesn't rely on unqualified-name resolution the way `SET search_path` does.
- **Lead:** `nestjs-cls` (continuation-local-storage wrapper for NestJS) came up repeatedly as the community-standard library for AsyncLocalStorage-based tenant-context propagation but was not fetched directly this round — worth pulling its official docs/README for the canonical NestJS pattern and version/compatibility info.
- **Lead:** `knex-tenanty` and `knextancy` (GitHub packages surfaced in the first search) are small community libraries specifically for Knex multi-tenant schema middleware — not evaluated this round; worth a maintenance/last-commit check if the team considers using a library rather than hand-rolling.

## What was searched for but NOT found

- No production write-up documenting `CREATE SCHEMA ... LIKE` or plpgsql `clone_schema()`-style template cloning as a validated technique for Knex/NestJS tenant provisioning (only "migrate fresh" pattern substantiated).
- No source directly confirming whether Knex's dynamic-schema migration limitation (#3034) persists in current (3.x) Knex releases — the only evidence is a 2019 issue against 0.16.3.
- No source specifically discussing `withSchema()` + connection-pool interaction edge cases (e.g., whether `withSchema()` calls are per-query-safe under a shared `pg` pool with concurrent tenants, versus session-level `SET search_path` which is documented as pool-unsafe). This is an important asymmetry the brief's Q2 asks about directly, and while `withSchema()` is described by the community-blog author (claim 1) as the "more robust" choice specifically because it avoids the session-state pooling hazard that plagues `search_path`, no official Knex/node-postgres source was found stating this explicitly — it is inferred by combining claim 1 (author's stated reasoning, medium confidence) with claim 6 (ClickHouse's documented pooling hazard for session-scoped `search_path`, high confidence, though that source discusses raw SQL/session variables rather than Knex specifically).
- No named-author source discussing "public schema leakage" as a distinct, specific pitfall for Knex/NestJS schema-per-tenant (e.g., a default/misconfigured `search_path` falling through to `public` and silently querying/creating objects in the shared `public` schema). The closest is the general search_path-hijacking mention (claim 11, unverified) and the no-DB-level-enforcement point (claim 8).
