- (claim) ref=[R1] status=verified class=patterns pub=2026-08 — PgBouncer transaction-mode pooling breaks session-level SET search_path (leaks/loses tenant scoping across pooled connections); safe alternatives are per-query knex.withSchema()/schema-qualified queries or transaction-scoped SET LOCAL, not session-level SET. Independently confirmed via PgBouncer GitHub issue #1313, Postgres mailing-list thread, and 2x 2026 vendor engineering posts (ClickHouse, PlanetScale).
- (claim) ref=[R2] status=verified class=versions/compatibility pub=2026-05 — CVE-2026-44680 / GHSA-cfw5-68c4-ffqp: real, published SQL-injection vulnerability in @mikro-orm/knex and @mikro-orm/sql (all versions <6.6.14) reachable via attacker-influenced strings passed to qb.withSchema(name) and equivalent multi-tenant schema APIs; root cause is unescaped SQL-identifier quoting, a generic class that applies to any hand-rolled .withSchema(tenantId) call, not just MikroORM. Confirmed independently via GitLab Advisory DB and GitHub Security Advisory directly.
- (claim) ref=[R3] status=disputed class=patterns pub=2026 — Practical schema-per-tenant scaling ceiling is disputed across sources by an order of magnitude: Citus docs say reconsider above ~10,000 schemas (catalog-cache memory per backend); PlanetScale/other 2026 engineering posts say degradation from as low as a few hundred tenants. Reconciled: the real driver is TOTAL catalog object count (schemas x tables x indexes x constraints per tenant), not raw schema count — a documented real-world case (~1,200 schemas x ~200 tables = ~240,000 tables) saw 2-hour migration runs and severe planner slowdown, consistent with Citus's own stated mechanism (per-backend catalog cache over total objects). For a platform where tenants create their own dynamic tables (uncapped tables/tenant), the effective ceiling is far below 10,000 tenants unless tables-per-tenant is bounded.
- (claim) ref=[R4] status=unverified class=landscape pub=2026 — No public source discusses schema-per-tenant combined with tenant-initiated dynamic/user-defined table creation specifically; this combination appears undiscussed in current public engineering writing. Flagged as a genuine coverage gap, not a confirmed absence of risk.
- (claim) ref=[R5] status=verified class=versions/compatibility pub=2016-2019 — Knex.js has no native multi-schema migration tracking; the canonical open issue (knex/knex#1138) has been open since 2016. A 2019 issue (knex/knex#3034) showed migrate.latest({schemaName}) historically ignored the schema param; current Knex 3.x status not independently re-verified this round (open follow-up).
- (claim) ref=[R6] status=verified class=patterns pub=2026 — Reliable NestJS tenant-context propagation pattern is middleware/interceptor extracting tenant ID from a verified JWT claim (never client-supplied body/header) into Node AsyncLocalStorage, avoided via .run() not .enterWith(); NestJS REQUEST-scoped providers were tried and abandoned by at least one production account due to performance/scope-cascade cost.

- (claim) ref=[3] status=overturned class=versions/compatibility pub=2026-08 — CORRECTION to prior unverified status: migrate.latest({schemaName}) does NOT ignore the schema option and was never a bug — Knex core maintainer (kibertoad, 2019-03-09 comment on knex/knex#3034) confirmed schemaName only relocates the knex_migrations/knex_migrations_lock tracking tables, never scopes migration DDL. Independently re-confirmed against current official Knex docs (knexjs.org/guide/migrations) with identical wording today. Correct pattern: knex.withUserParams({schema}) + knex.schema.withSchema(knex.userParams.schema) inside each migration file. This is a correctness trap for naive implementations, not a missing/broken feature.
