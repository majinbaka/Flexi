- (decision) Metadata layer (DynamicTable/DynamicField definitions: table/column names, dataType, required, config) moves fully into each tenant's own Postgres schema, managed via Knex -- NOT via the existing Prisma DynamicTable/DynamicField models (which are row-level tenantId in public schema, matching every other Flexi metadata table). User confirmed this after being shown the tradeoffs: (a) tenant provisioning must run its own metadata-table DDL/migration per tenant schema via Knex, not a single global Prisma migration; (b) Prisma's DynamicTable/DynamicField models become dead/unused -- unclear yet whether they're dropped or left as deprecated; (c) diverges from spec-flexi-core-scaffold.md's frozen row-level-tenantId decision, scoped specifically to this module; (d) cross-tenant metadata queries (e.g. platform-wide dynamic-table count) require iterating tenant schemas instead of one Prisma query. Binds: all metadata reads/writes for this module go through TenantKnexService, never PrismaService. Prevents: a split-brain where some metadata calls hit Prisma's public-schema models and others hit tenant-schema Knex tables.
- (question) Follow-up needed at Finalize: existing Prisma DynamicTable/DynamicField models (schema.prisma:198-237) are now superseded by this decision. Options: drop them in a migration, or leave as deprecated/unused. Not yet decided -- surface to user before closing.
- (assumption) SPEC.md (spec-dynamic-table-builder) will need a follow-up update after this spine finalizes, since its Constraints section currently doesn't address the metadata-location question explicitly (it was ambiguous, and this spine is the first place it's resolved). Standard Finalize step 6 offer (adopt spine as spec companion) should also carry this specific delta back to the user.
- (decision) DynamicTables backend module is the sole owner of DDL execution against tenant schemas. Any future module (Workflow Builder, Page Builder, etc.) that needs a dynamic table's structure changed does so by calling DynamicTables module's service API, never by issuing its own TenantKnexService DDL calls directly. Binds: one guardrail-check point (CAP-8), one migration-record point (CAP-5), one DDL-queue point (CAP-6) for the whole platform. Prevents: two modules independently issuing structural changes to the same tenant table through different code paths, e.g. one honoring the queue/lock_timeout discipline and another bypassing it.
- (direction) User confirmed centralized DDL ownership over a decentralized per-module-DDL alternative.
- (decision) DML validation uses a generated-and-cached validation schema per dynamic table, not per-request dynamic rebuild. On table create (CAP-1) and every field edit (CAP-2), DynamicTables module (re)generates a validation schema (class-validator-compatible shape, matching this codebase's DTO convention) from that table's DynamicField records and holds it in an in-memory cache keyed by table id, invalidated synchronously on the same CAP-2 edit that changed it. Binds: DML request handlers always read the cached generated schema, never re-derive validation rules from raw DynamicField rows per-request. Prevents: validation drift between what CAP-3 promises and what a given request actually checks, and avoids a full per-request metadata-table round trip for every row write.
- (constraint) Cache is in-memory per backend instance (not Redis-shared), accepted tradeoff: brief cross-instance staleness window after a CAP-2 edit until each instance's own cache invalidates/rebuilds, versus added pub/sub invalidation complexity of a Redis-shared cache. User confirmed in-memory over Redis-shared for this first cut.
- (decision) DML REST routes use a generic id-parameterized shape: /api/tables/:tableId/rows (and sub-paths for single-row CRUD, e.g. /api/tables/:tableId/rows/:rowId). One controller resolves :tableId against DynamicTable metadata to find the target physical table, rather than generating per-table routes. User confirmed cuid tableId over a slug-based route.
- (decision) Default platform-wide guardrail ceilings (used when a tenant hasn't overridden its own CAP-8 settings): 100 dynamic tables per tenant schema, 50 columns per dynamic table. Conservative starting point, explicitly revisitable once real usage data exists -- not a benchmarked figure, chosen over a looser 500/100 alternative closer to the unsourced research numbers. Resolves SPEC.md's remaining open question on default ceiling values.
- (decision) BullMQ DDL worker runs in-process within the same NestJS backend app/deployment unit as the API (registered as a BullMQ worker provider inside DynamicTables module), not as a separately deployed service. Matches Flexi's current single-deployment-unit scale; no new deploy topology introduced. Revisit if DDL job volume or isolation needs later justify splitting it out.
- (constraint) REDIS_URL becomes a required (not optional) env var once this module ships, since the in-process worker needs a live Redis connection to function -- env.validation.ts's existing Joi.string().optional() declaration for REDIS_URL must change to required, following the same pattern as DATABASE_URL.
- (decision) Correction/clarification: the DML routing decision's phrase 'resolves :tableId against DynamicTable metadata' means the tenant-schema Knex-managed metadata table (per the metadata-location decision above), NOT the Prisma DynamicTable model. Same applies everywhere else in this memlog that says 'DynamicTable metadata' or 'DynamicField records' from this point forward -- all such lookups go through TenantKnexService against the tenant-schema metadata tables, never PrismaService.
- (decision) CAP-6's BullMQ job queue uses BullMQ's PostgreSQL backend (new in BullMQ 6.0.0, released 2026-07-30), NOT Redis. Reuses the existing DATABASE_URL/pg connection this codebase already has -- no ioredis dependency, no reliance on the docker-compose Redis service. User confirmed after web-verification review flagged that AD-8's original Redis rationale ('infra already exists') was undercut by BullMQ's new Postgres-native option, which better matches this codebase's existing single-datastore posture. Supersedes the earlier Redis+BullMQ decision and its REDIS_URL-required constraint.
