# Epic 3 Context: Operator Visibility, Handoff, And Failure Review

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Ops and SysAdmins need a Super Admin dashboard surface to monitor tenant onboarding progress, inspect attempt history and detail, safely copy successful handoff data, and escalate failures — without exposing remediation controls in Phase 1. This epic covers the read/observability layer only: the tenants list, a live provisioning attempt timeline, a success handoff panel, a view-only failure/escalation panel, an audit detail drawer, and cross-cutting responsive/accessible behavior. It does not implement provisioning logic, tenant creation, schema/bootstrap work, or setup-link generation itself — those are owned by Epic 1 (intake) and Epic 2 (provisioning), which this epic's UI reads and displays.

## Stories

- Story 3.1: Tenants List And Onboarding History
- Story 3.2: Provisioning Attempt Detail And Timeline
- Story 3.3: Success Handoff Result
- Story 3.4: Failure Detail And View-Only Escalation
- Story 3.5: Audit Detail Drawer
- Story 3.6: Responsive, Accessible Operational UX

## Requirements & Constraints

- The Super Admin UI must show overall attempt status (`PROVISIONING`, `ACTIVE`, `FAILED`; timed-out attempts resolve to `FAILED` with timeout detail) and a step checklist/timeline for: permission check, attempt reservation, tenant creation, schema provisioning, Tenant Admin role prep, First Admin creation, role assignment, activation, and audit finalization.
- Progress updates come from MVP polling of `GET /api/v1/super-admin/tenants/:id/status`; no realtime push is required.
- Attempt detail must show actor, timestamps, tenant name, subdomain, Plan, First Admin email, current status, step status, and failed step when applicable, plus a basic safe error message/code suitable for escalation. Never expose secrets or plaintext setup tokens.
- Onboarding history (tenants list) supports MVP filters only: status, subdomain/keyword search matching tenant name or slug, and `created_at` date range. Actor filtering is explicitly deferred — actor name is displayed but not filterable.
- Phase 1 failure controls are view-only: no Retry, Cleanup, force-activate/force-fail, or manual state-transition controls anywhere in the UI. Failed-attempt screens must direct Ops to `#ops-escalation-flexi` and `https://wiki.internal.flexi/runbooks/tenant-provisioning-failure`.
- The Setup Link is generated by Epic 2's backend; this epic's job is only to display it as the primary handoff mechanism with copy affordance, and make clear whether backup automated email was also attempted (e.g., `Email Delivery Failed (Copy Link Manually)`).
- If the setup token/link cannot be safely re-read after a reload, show safe metadata plus a clear regeneration message via the approved flow (`POST /api/v1/super-admin/tenants/:id/setup-link`) — never invent or expose the secret again.
- Audit evidence (`TenantOnboardingAuditLog`) is permanent and must display actor, request identity, safe payload metadata, step outcomes, compensation status, and final state — while omitting plaintext passwords, plaintext setup tokens, secrets, stack traces, and raw SQL.
- `PROVISIONING`, `FAILED`, and `SUSPENDED` tenants must never be presented as login-ready or usable; customer handoff controls are hidden whenever the tenant is not `ACTIVE`.
- Accessibility target is WCAG 2.2 AA (NFR9 states 2.1 AA as a floor, UX docs target 2.2 AA): programmatic labels, `aria-describedby`/`aria-invalid` on validation, status conveyed via text+badge/icon (never color alone), polite live-region announcements for timeline/step changes and copy confirmations (`Copied [value name]`), 44px minimum touch targets, and focus order following visual reading order.
- Responsive behavior: `md+` keeps the visible sidebar and may use multi-column layouts (timeline beside audit/result metadata); below `md`, sidebar becomes a drawer, form/detail sections stack, timeline stays a vertical list, audit becomes a full-screen sheet, and tables scroll horizontally within their own container.
- Operational microcopy must name the specific field or backend step, the consequence, and the next action — no vague "something went wrong" copy, no celebratory animations/confetti.

## Technical Decisions

- Consumed API surface (owned by Epic 1/2, read by this epic): `GET /api/v1/super-admin/tenants` (list/history), `GET /api/v1/super-admin/tenants/:id/status` (polling), `POST /api/v1/super-admin/tenants/:id/setup-link` (regeneration trigger only — the button/flow lives here, generation logic does not).
- Standard response envelope: `{ success, data, error, meta: { timestamp, requestId } }`.
- Reuse the existing authenticated Flexi app shell and component set: `Layout`, `Sidebar`, `TopNav`, `PageHeader`, `Button`, `Input`, `Select`, `Card`, `Table`, `Badge`, `Icon`.
- Route-level and control-level permission gating: only SystemUsers with `system.tenants.onboard` see onboarding-related create/regenerate actions; users without it get controls hidden (list) or a permission-denied message (direct route access). No `isSuperAdmin` bypass concept.
- New custom components needed for this epic: `provisioning-progress-timeline` (vertical stepper: `waiting`/`running`/`succeeded`/`failed`/`compensated` states), `status-badge` (maps `PROVISIONING`/`ACTIVE`/`FAILED`/`SUSPENDED`, plus `failed-needs-manual-cleanup` as a warning/manual-attention variant), `idempotency-notice`, `result-panel`, `audit-detail-drawer`, `empty-state`.
- Attempt status polling must be resilient: on polling failure, keep the last known step visible and show a single reconnection notice (not repeated toasts); updates must never reset scroll position, collapse an already-expanded failed step, or clear a "copied" confirmation state.
- Use Inter for product text; JetBrains Mono (code-small typography token) exclusively for machine identifiers: tenant id, schema name, setup token snippets, idempotency keys, URLs, audit resource ids.
- Design tokens: existing Flexi token system in `apps/frontend/src/styles/tokens.css` (Stitch-synced) — no new decorative palette. Status color mapping: primary = current/running step, secondary-fixed-dim = success/`ACTIVE`, tertiary-fixed = warning/`SUSPENDED`/manual-cleanup, error/error-container = `FAILED`/destructive. Full border-radius reserved for status badges only; avoid nested cards; prefer borders/tonal surfaces over shadow.
- No mockups/wireframes exist yet for these surfaces — EXPERIENCE.md and DESIGN.md spines are the source of truth and win on conflict with any future imports.

## UX & Interaction Patterns

- Information architecture: Tenants list (reached via sidebar `tenants` module) → Onboard New Tenant (primary action on Tenants list, not a separate sidebar item, owned by Epic 1) → Provisioning attempt detail (reached from submit success, a tenants-list row, or idempotent retry lookup) → Tenant success result (attempt detail when `ACTIVE`) / Failure and cleanup detail (attempt detail when `FAILED` or `failed-needs-manual-cleanup`) → Audit log detail (drawer/sheet opened from attempt detail).
- Tenants list: rows show tenant name, slug, lifecycle status, plan, created date, latest attempt status, actor name, and onboarding-specific action buttons; row click opens tenant/attempt detail. Preserve list filters when navigating back from attempt detail.
- List states: cold load shows skeleton table rows sized like the final table; empty inventory shows `No tenants yet.` with `Onboard New Tenant` as the only primary action (if permitted); no-matching-filters state uses concise copy with no motivational language.
- Operator-facing step vocabulary for the timeline (map backend step → label → completion signal): Authorize SystemUser → "Checking permission"; Reserve onboarding attempt → "Reserving onboarding attempt"; Create Tenant → "Creating tenant record"; Provision tenant schema → "Provisioning tenant schema"; Ensure Tenant Admin role → "Preparing Tenant Admin role"; Create first admin actor → "Creating first admin account"; Assign role → "Assigning Tenant Admin role"; Activate Tenant → "Activating tenant"; Finalize audit → "Finalizing audit".
- Long-running threshold (~30s, assumption): show "Still working. You can leave this page and return to the attempt."
- Success result panel: shows tenant URL, First Admin email, setup link/token handoff, tenant id, and schema name where safe; copy buttons are icon+text, announce `Copied [value name]` via `aria-live` without moving focus, and never mutate server data. Machine identifiers use monospace/code-small styling.
- Failure and cleanup detail: failed step expands by default with safe error detail and compensation state (completed / partially completed / requires manual cleanup); exact stuck resource ids are listed when available; customer handoff controls are hidden entirely; if compensation status is missing/ambiguous, show "Manual review required. Audit detail is incomplete." and keep everything view-only.
- Audit detail drawer: right-side drawer on desktop, full-screen sheet on small screens; lists permanent events, step outcomes, safe payload metadata, and safe identifiers; dismissing it preserves attempt-page scroll/state; never shows plaintext secrets, stack traces, or raw SQL.
- Idempotency notice: appears on form and attempt detail, explains that a retry with the same key returns/resumes the existing attempt, and shows the existing attempt id when available.
- Interaction primitives: click/tap only (no drag); `Esc` closes the topmost drawer/dialog; back navigation from attempt detail returns to Tenants list with prior filters intact. Banned: celebratory animations/confetti, infinite scroll, hover-only critical actions, spinner-only screens hiding background work, stacked modals deeper than one.
- Voice/tone examples to follow: "Provisioning schema...", "Failed at role assignment. Compensation completed.", "Copy setup link" — avoid vague copy like "Something went wrong" or "Almost done!".

## Cross-Story Dependencies

- Depends on Epic 1 (Onboarding Attempt creation, idempotency identity, actor/permission data) and Epic 2 (tenant lifecycle transitions, step outcomes, Setup Link generation, `TenantOnboardingAuditLog` records) as the data source this epic's UI reads and polls — this epic implements no provisioning or audit-writing logic itself.
- Story 3.2 (attempt timeline) is the shared shell that Story 3.3 (success result) and Story 3.4 (failure detail) render into once an attempt reaches a terminal state; both depend on 3.2's polling/state-preservation behavior.
- Story 3.5 (audit drawer) is invoked from attempt detail (3.2/3.3/3.4) and must not disturb their underlying page state when opened or dismissed.
- Story 3.1 (tenants list) supplies the navigation entry point into attempt detail (3.2) and must preserve its own filter state across that round trip.
- Story 3.6 (responsive/accessible UX) is a cross-cutting constraint applied to all other stories in this epic (3.1–3.5), not a standalone surface.
