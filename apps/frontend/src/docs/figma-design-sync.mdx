# Figma Design Sync Workflow

This document explains how designs from the project's Figma file get
turned into frontend code. There is no automated design-to-code
pipeline -- this is a lightweight, manual, zero-new-dependency process
that every future feature spec touching UI must follow.

## Reference

- **Figma file key:** `zhLrZDSvhw2cHAUWR0cnOU` (file "Untitled")
- **MCP server name:** `figma` (registered locally via
  `claude mcp add figma -s local -e FIGMA_API_KEY=... -- npx -y figma-developer-mcp --stdio`;
  the API key lives only in local MCP config, never in a git-tracked
  file)
- **Token file:** [`apps/frontend/src/styles/tokens.css`](../styles/tokens.css)
  -- imported globally from [`apps/frontend/src/main.tsx`](../main.tsx)
- **Ledger:** [`_bmad-output/implementation-artifacts/figma-sync-ledger.md`](../../../../_bmad-output/implementation-artifacts/figma-sync-ledger.md)

### Getting a Figma personal access token

Each contributor generates their own token and registers it locally --
it is never shared or committed:

1. In Figma, go to **Settings -> Personal access tokens** and generate
   a new token. It only needs **read access to files** (no write/admin
   scopes are required for this workflow).
2. Run the `claude mcp add ...` command above yourself, substituting
   your token for `FIGMA_API_KEY`.
3. Because the server is registered with `-s local` (local scope, not
   committed anywhere), this is a **per-contributor, per-machine**
   step -- every new contributor (and every new machine/clone) must
   generate their own token and re-run the registration; it does not
   carry over from the repo or from another contributor's setup.

### Session reload note

If the `figma` MCP tools aren't visible/callable in your Claude Code
session, the server was registered or reconnected after the session
started. Reload the Claude Code session so it picks up the newly
available MCP tools, then retry.

## Why this exists

The Figma file is the source of truth for the app's visual design, but
the project intentionally has no design-token or component-library
system yet (see the "Design Notes" in
`_bmad-output/implementation-artifacts/spec-figma-design-sync.md`).
Instead of restyling everything at once, the whole file is synced
**gradually, one feature at a time**: whenever a feature spec's scope
includes UI, the implementer pulls the relevant Figma frame, lands any
new design values into the shared token file (reusing existing tokens
first), builds the component against those tokens, and records the
mapping in the ledger.

## Per-feature workflow

Follow these steps whenever a feature spec's scope includes UI:

1. **Fetch the frame.** Use the `figma` MCP server's tools against file
   key `zhLrZDSvhw2cHAUWR0cnOU` to pull the specific frame/node your
   feature implements (get its layout, colors, typography, spacing,
   and the node-id). To find a frame's node-id, select it in the
   Figma UI and copy its share link, or use the MCP tools' own
   node/frame listing. Note the two formats you'll see for the same
   id: the REST API / ledger form uses a colon (`12:34`), while
   Figma's UI share-link URLs use a dash in the `node-id` query
   param (`node-id=12-34`) -- convert dash to colon (or vice versa)
   as needed; they refer to the same node.
2. **Extract tokens into `tokens.css`, reusing existing ones first.**
   Before adding a new CSS custom property to
   `apps/frontend/src/styles/tokens.css`, check whether an existing
   token already matches the value (same color, spacing unit, font
   size, radius, etc.). Only add a new token under the appropriate
   category comment (colors / typography / spacing / radii) when
   nothing existing fits.
3. **Implement the component against tokens.** Style the
   component/page using `var(--token-name)` references into
   `tokens.css` rather than hardcoding the raw values from Figma
   inline. (This spec does not migrate the existing inline-style
   components such as `Layout.tsx` / `Sidebar.tsx` -- that happens
   incrementally as each of them is next touched by a feature spec.)
4. **Update the ledger.** Add one row to
   `_bmad-output/implementation-artifacts/figma-sync-ledger.md` for
   the frame you just implemented, with columns:

   `Figma node | node-id | Frontend path | Status | Last synced | Notes`

   **Status legend** (allowed values for the Status column):
   - `in-progress` -- sync of this frame has started but the component
     doesn't yet fully match Figma.
   - `done` -- the component matches the Figma frame as of "Last
     synced".
   - `stale` -- the Figma frame has changed since "Last synced" and
     the component needs another pass through steps 1-4 below.

   Example (illustrative -- do not copy verbatim, this row does not
   exist yet):

   ```
   | Login screen | 12:34 | apps/frontend/src/pages/LoginPage.tsx | done | 2026-08-20 | colors + spacing only |
   ```

### Re-syncing a frame whose Figma design changed

If a frame's Figma design changes after it was already implemented
(mark its ledger row `stale` when you notice this, or when told the
design changed), treat it as a fresh pass through steps 1-4 above:
re-fetch the frame, extract/update tokens, update the component. The
one difference is step 4 -- **update the existing ledger row** for
that frame instead of adding a new one: bump "Last synced" to today's
date, set Status back to `done` (or `in-progress` if only partially
re-synced), and note in "Notes" what changed.

## Constraints

- **Dependency-free by default.** This workflow deliberately avoids
  Tailwind, CSS-in-JS, or a component library to match the project's
  current scaffold phase. If a feature's design complexity outgrows
  plain CSS custom properties, that's an "ask first" moment -- escalate
  before adding a new frontend styling dependency, don't default to
  one.
- **No specific page is pre-restyled.** Tokens and this workflow are
  infrastructure; actual screens are implemented incrementally by the
  feature specs that touch them.
- **Secrets stay out of git.** The Figma personal access token is
  configured only via local (untracked) MCP server config, never
  committed to any file in this repository.
