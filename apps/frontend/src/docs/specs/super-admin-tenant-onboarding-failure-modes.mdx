# Failure Modes

This companion is part of `SPEC-super-admin-tenant-onboarding`. It defines the rollback and audit obligations behind CAP-6 and CAP-7.

## Invariants

- Audit evidence is append-only for this workflow: a rollback may compensate product state but never deletes the attempt record or its step records.
- A tenant becomes product-visible only after the final activation step succeeds.
- Tenant lifecycle state is held directly on `Tenant.status`: `PROVISIONING`, `ACTIVE`, `FAILED`, or `SUSPENDED`.
- Every step writes a started/succeeded/failed outcome, including the compensation action taken after a failure.
- A retry with the same onboarding idempotency key returns or resumes the recorded attempt instead of starting an independent second attempt.
- `TenantOnboardingAuditLog` stores per-step outcomes, payload metadata, and compensation status as JSONB and is retained permanently.
- Plaintext passwords, setup tokens, and secret values are never written to audit.

## Provisioning Steps

| Step | State Created | Success Condition |
| --- | --- | --- |
| Authorize SystemUser | none | Caller is a `SystemUser` with `system.tenants.onboard`. |
| Reserve onboarding attempt | `TenantOnboardingAuditLog` + idempotency record | Request key, actor, tenant slug/name, and first-admin email are recorded without secrets. |
| Create Tenant | public-schema Tenant row | Tenant exists with `Tenant.status = PROVISIONING` and cannot be used for login or tenant routes. |
| Provision tenant schema | Postgres schema + bootstrap objects | Schema name follows `tenant_<Tenant.id CUID>` (for example `tenant_clx1234567890`), resolves through the tenancy layer, and required bootstrap migrations have completed. |
| Ensure Tenant Admin role | tenant-scoped Role + RolePermission rows | Role code/name are `TENANT_ADMIN` / `Tenant Administrator`; grants `tenant:*` if supported, otherwise all `TENANT`-scope permissions, and no `SYSTEM` permissions. |
| Create first admin actor | AuthAccount + TenantUser + setup token | First admin has one login identity, one TenantUser actor for the new tenant, and the API response returns a one-time short-lived `setupToken`. |
| Assign role | TenantUser-role link | First admin holds the Tenant Admin role before activation. |
| Activate Tenant | `Tenant.status` transition | Tenant becomes `ACTIVE` only after every previous step has succeeded. |
| Finalize audit | audit final status | Attempt records success with created identifiers safe to expose; no plaintext setup token is recorded. |

## Compensation Matrix

| Failure Point | Required Outcome |
| --- | --- |
| Authorization fails | No onboarding attempt that implies tenant creation; standard security/audit logging may still record denied access. |
| Attempt reservation fails | No tenant, schema, role, AuthAccount, or TenantUser is created. |
| Tenant row creation fails | Attempt records failure; no tenant schema or first-admin state is created. |
| Schema provisioning fails after Tenant row exists | Tenant transitions to `FAILED`; any created schema is dropped if known complete enough to drop safely; audit records the schema cleanup result. |
| Role bootstrap fails | Tenant transitions to `FAILED`; created role/permission links are removed when possible; schema cleanup follows the same rule as schema failure. |
| First admin AuthAccount/TenantUser creation fails | Tenant transitions to `FAILED`; partial AuthAccount/TenantUser rows are removed or deactivated; role and schema cleanup outcomes are recorded. |
| Role assignment fails | Tenant transitions to `FAILED`; the first admin actor is removed or deactivated; role and schema cleanup outcomes are recorded. |
| Activation fails | Tenant remains or transitions to `FAILED`; prior state is either compensated or the attempt is marked failed-needs-manual-cleanup with exact stuck resources. |
| Compensation fails | Attempt final status is failed-needs-manual-cleanup; audit identifies every resource requiring operator action. |

## Manual Cleanup Threshold

The workflow may stop compensating and mark `failed-needs-manual-cleanup` only when continuing automatic cleanup risks deleting ambiguous live state. That status is acceptable only if `Tenant.status` is not `ACTIVE` and the audit record lists the exact Tenant id, schema name, AuthAccount id, TenantUser id, role id, and failed compensation step known at the time.
