## Intent

**Problem:** `POST /api/auth/login` and `POST /api/auth/refresh` have no attempt-throttling, so password/refresh-token guessing is currently unbounded. Deferred from `spec-core-authentication.md` (step-04 blind-hunter review).

**Approach:** Add `@nestjs/throttler` and apply a stricter, per-route rate limit to `login` and `refresh` only (not global default), keyed by client IP. Limits are configurable via `ConfigService`/`env.validation.ts`, not hardcoded, matching this codebase's existing tunable convention.

## Boundaries & Constraints

**Always:**
- Limit applies only to `POST /api/auth/login` and `POST /api/auth/refresh` — no other route's behavior changes.
- Limit config (`ttl`, `limit`) comes from `ConfigService` via new `env.validation.ts` entries with sane defaults (so no `.env` change is required for existing setups to keep working).
- Throttled requests return NestJS's standard 429 response (default `ThrottlerGuard` behavior) — do not hand-roll a custom response shape.
- In-memory storage (the package default) — no new infra dependency (no Redis wiring), since this app runs single-instance today and `REDIS_URL` is not consumed anywhere else in the codebase.
- Existing `auth.service.spec.ts` unit tests must keep passing unmodified (guard is applied at the controller/route level, not inside `AuthService`).

**Ask First:** none.

**Never:**
- Do not apply a global default throttle to every route — scope is login/refresh only.
- Do not wire Redis-backed storage or any multi-instance-safe store.
- Do not add throttling to `logout` or `me`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Under limit | N requests to `/api/auth/login` within `ttl`, N < configured limit | 200/401 as normal per credentials | N/A |
| Over limit | N+1th request to `/api/auth/login` within same `ttl` window, from same IP | 429 Too Many Requests | Standard Nest `ThrottlerException` response |
| Refresh over limit | Same as above but on `/api/auth/refresh` | 429 Too Many Requests | Standard Nest `ThrottlerException` response |
| Window reset | Request arrives after `ttl` window has elapsed | Counter resets, request processed normally | N/A |
| Unaffected route | Requests to `/api/auth/me` or `/api/auth/logout` exceeding what would be login's limit | No 429 — these routes are unthrottled | N/A |

## Design Notes

`ThrottlerGuard` is applied per-route via `@UseGuards()` rather than registered as a global `APP_GUARD`, so only `login`/`refresh` are affected — avoids retrofitting throttle behavior onto every other stub module's routes as an unreviewed side effect. `ThrottlerModule.forRootAsync` is scoped to `AuthModule` (not `AppModule`) since no other module needs it yet; this keeps the change local to the one module actually being touched.

## Spec Change Log

- **Finding (verification-gap review, loop 1):** `ThrottlerGuard`'s actual rate-limiting behavior was never exercised by any test in the first implementation. `auth.controller.spec.ts` only asserted `GUARDS_METADATA` reflection (decorator presence), and the e2e suite never sent enough requests to reach the configured limit. A miswired or no-op guard (e.g. options resolving to `Infinity`, `canActivate` always returning `true`) would have shipped with all tests green.
  - **Amended:** `## Code Map`, `## Tasks & Acceptance`, and `## Verification` now require a real e2e test in `apps/backend/test/app.e2e-spec.ts` that sends more than the configured limit of requests to `login`/`refresh` and asserts an actual HTTP 429 response. The route-scoping metadata test in `auth.controller.spec.ts` is retained but explicitly scoped as insufficient on its own. Also added: `AUTH_THROTTLE_TTL`/`AUTH_THROTTLE_LIMIT` must use `.integer().positive()` Joi validation (was bare `.number()`), so `0` or a negative value fails startup instead of silently disabling or breaking the limiter (a cheap, directly-in-scope hardening the blind-hunter review also flagged).
  - **Known-bad state avoided:** the rate-limiting feature regressing to a complete no-op with CI staying green, and a startup-time misconfiguration (`AUTH_THROTTLE_LIMIT=0`) either locking out all logins or disabling protection entirely with no validation error.
  - **KEEP:** the overall design — `@nestjs/throttler`, per-route `@UseGuards(ThrottlerGuard)` scoped to `AuthModule` only, in-memory storage, config via `ConfigService`/`env.validation.ts` — was sound and is unchanged. The route-scoping metadata test (`auth.controller.spec.ts`) was good, correctly-targeted coverage for its one narrow claim (which routes carry the guard) and should be re-derived as-is, just no longer treated as sufficient for the 429-firing behavior itself. Blind-hunter findings about IP tracking behind a reverse proxy, `x-tenant-id`-based fan-out, frontend 429 handling, and ops/deployment documentation were considered and deliberately left out of scope (pre-existing infra gaps or separate shippable units, not caused by this change) — do not re-introduce them as scope in the re-derivation.
