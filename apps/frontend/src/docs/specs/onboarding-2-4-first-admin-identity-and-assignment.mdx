## Intent

**Problem:** After Story 2.3, a `PROVISIONING` tenant has a schema, bootstrap tables, and business-data RBAC defaults, but no login path into the workspace — no First Admin identity exists, and the real (public-schema, authorization-gating) `TENANT_ADMIN` role has never been created or assigned for that tenant.

**Approach:** Add a fourth sequential provisioning step, `firstAdminAssigned`, that creates exactly one `AuthAccount` + `TenantUser` (using the attempt's `firstAdminEmail`, a random unusable password placeholder, and `status: 'pending_setup'`), ensures a public-schema `Role` row `{ tenantId, name: 'TENANT_ADMIN' }` exists with tenant-scoped permissions only, and assigns that role to the new `TenantUser` — all before any later step (Story 2.5/2.6) can activate the tenant.

## Boundaries & Constraints

**Always:** Resolve the First Admin's email via a fresh `readAttemptSafePayload(attemptId)` re-query (mirror `readAttemptStatus()`'s targeted `$queryRaw`-by-id pattern) inside the new step — do not thread `safePayload` through both `startLifecycle()` call sites. Create the `AuthAccount` + `TenantUser` inside one `prisma.$transaction`. Generate the placeholder password via `bcrypt.hash(randomUUID(), 10)` (never a guessable fixed string, never left blank) since real setup happens in Story 2.5. Set the new `TenantUser.status` to `'pending_setup'`. Ensure the `Role` via `prisma.role.upsert({ where: { tenantId_name: { tenantId, name: 'TENANT_ADMIN' } }, ... })` (exact upsert-by-natural-key shape `prisma/seed.ts:77-85` uses for `'Admin'`), then grant it every currently-seeded `TENANT`-scope `Permission` via `RolePermission` (mirror `assignPermissionToRole()` in `prisma/seed.ts`, enforcing the same tenant-role-never-holds-SYSTEM-scope rule). Idempotent replay: if a `TenantUser` already exists for this `tenantId` (from a prior partial run), reuse it and its `AuthAccount` rather than creating a second one; if the `Role` already exists, reuse it. Record one step outcome (`first_admin_assigned`) succeeded/failed on the attempt, following the exact `bootstrapTenantSeed()` template (CLS `runWith`, try/succeeded/catch-log-failed-rethrow, safe error code `FIRST_ADMIN_ASSIGNMENT_FAILED`). Never activate on failure; rethrow for BullMQ retry.

**Ask First:** Exact `TENANT_ADMIN` permission set if it should be narrower than "every seeded TENANT-scope permission"; whether `TenantUser.name` should default from the email local-part or stay `null` until real setup.

**Never:** Reuse or link to the tenant-schema Knex `roles`/`role_permissions` tables from Story 2.3 (`tenant-seed.service.ts`) — those are a disconnected business-data catalog, not the authorization-gating public-schema `Role`. Create a `SystemUser` for the First Admin, or let one `AuthAccount` back both a `SystemUser` and a `TenantUser` (check-before-create, since no DB constraint enforces this). Set `Tenant.status = ACTIVE` in this story. Implement setup-link generation or email delivery (Story 2.5). Use session-level `SET search_path` (n/a here — this step is public-schema/Prisma only, no tenant-schema Knex access).

**Acceptance Criteria:**

- Given required tenant bootstrap state exists, when First Admin creation runs, then Flexi creates exactly one `AuthAccount` and exactly one `TenantUser` for the tenant, and the `TenantUser` starts in `pending_setup` status.
- Given the First Admin's `AuthAccount` is created, then no `SystemUser` is backed by that same `AuthAccount`.
- Given the First Admin exists, when role assignment runs, then a tenant-scoped `Role` named `TENANT_ADMIN` exists (or is reused) and is assigned to the First Admin `TenantUser` before activation, holding only `TENANT`-scope permissions.
- Given a worker retry where the `TenantUser` and `TENANT_ADMIN` role already exist, when `assignFirstAdmin` runs again, then no duplicate `AuthAccount`/`TenantUser`/`Role` rows are created and `first_admin_assigned` is still recorded `succeeded`.
- Given the transaction fails mid-way, when it rolls back, then `first_admin_assigned` is recorded `failed` with a safe error code (no stack trace, no raw SQL, no password hash), the tenant remains `PROVISIONING`, and the error is re-thrown for BullMQ retry.

## Design Notes

**Why re-query `safePayload`:** `startLifecycle()` has two paths into `provisionTenantSchema()` (fresh attempt, already-linked-tenant retry); only the fresh path currently has `safePayload` in scope. A targeted re-fetch inside the new step (mirroring `readAttemptStatus()`) keeps both call sites symmetric without widening `provisionTenantSchema()`'s signature.

**Role name:** use `name: 'TENANT_ADMIN'` (epics.md FR11) for the provisioning-created role — distinct from `prisma/seed.ts`'s pre-existing demo `'Admin'` row, which is out of scope to rename.
