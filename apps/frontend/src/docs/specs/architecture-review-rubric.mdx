# Architecture Spine Review — Dynamic Database / Table Builder

**Target:** `apps/frontend/src/docs/specs/architecture.mdx`
**Reviewer role:** independent quality reviewer, rubric-based
**Verdict: PASS WITH FINDINGS**

The spine is unusually disciplined for a first-cut: every AD names the exact divergence it prevents, the Prisma-supersession is explicit rather than silent, and all 8 CAPs map to concrete owning code. It passes the core bar. The findings below are real gaps but none invalidate the spine's central design (single-owner Knex module, async DDL via BullMQ, per-tenant guardrails) — they're places where the spine either misstates the brownfield baseline, leaves a load-bearing dimension implicit, or hands the level below a coordination problem it should have foreclosed itself.

---

## Critical

None. No finding here would let two independently-built units diverge in a way the spine's own ADs fail to prevent, and nothing found contradicts brownfield reality in a way that would corrupt data or break tenant isolation.

---

## High

### H-1 — Existing `DynamicTablesModule` stub is not acknowledged; Structural Seed reads as greenfield and will collide with it

`apps/backend/src/modules/dynamic-tables/` already exists and is registered in `app.module.ts`. It is a real stub: `dynamic-tables.module.ts` wires a `@Controller('dynamic-tables')` with one `GET /api/dynamic-tables` route returning `{status:'not-implemented'}`, backed by `DynamicTablesService.getStatus()`. The spine's Structural Seed proposes `tables.controller.ts`, `rows.controller.ts`, and a `dynamic-tables.service.ts` with entirely different responsibilities (sole DDL/metadata owner, per AD-2/AD-5) inside the *same directory*, and never mentions the file it's colliding with or the route it's superseding.

This is exactly the kind of divergence-point the spine exists to close off: absent an explicit instruction, one implementer could delete the stub and rebuild the module fresh, another could leave `dynamic-tables.controller.ts`/`.service.ts` in place and add the new controllers alongside it — leaving a dead `GET /api/dynamic-tables` route and two `DynamicTablesService` classes (or a naming clash forcing an ad hoc rename) in the tree. The spine ratifies the brownfield Prisma models explicitly (AD-1) but is silent on this closer, more mechanical piece of brownfield reality.

**Fix:** Add one sentence to the Structural Seed or AD-2: "This supersedes the existing stub `DynamicTablesModule`/`DynamicTablesController`/`DynamicTablesService` in the same path — the stub's `GET /api/dynamic-tables` status route is deleted, not preserved alongside the new routes."

### H-2 — AD-8's stated rationale for keeping Redis in-process is factually wrong about what "new" means here

AD-8 says: "**Prevents:** Introducing a new deployment unit/topology this codebase doesn't otherwise have yet." But `docker-compose.yml` already defines and runs a `redis` service (`flexi-redis`, `redis:7`, with healthcheck) alongside `postgres`. Redis-the-infrastructure is *already in the topology* — what's actually new is (a) the application code depending on it (BullMQ worker, `ioredis` client) and (b) `REDIS_URL` moving from optional to required in `env.validation.ts`.

This doesn't break the AD's *rule* (in-process worker, no new deployment unit) — that rule stands on its own merits regardless of whether Redis was already provisioned. But a rationale that misstates the brownfield baseline is a credibility problem for a document whose whole job is to be the trustworthy source on brownfield-vs-new, and it's the kind of thing a story-writer might repeat verbatim ("we don't have Redis yet") into a story that then wastes time re-provisioning or hedging around infra that's already sitting in `docker-compose.yml`.

**Fix:** Reword to: "Prevents: introducing a new deployment unit/process topology — Redis infrastructure already exists in `docker-compose.yml`, but no backend code depends on it yet; this AD keeps the *consumer* (the DDL worker) inside the existing API process rather than spinning up a second service."

## Medium

### M-1 — CAP-8's numeric defaults are asserted as decided, contradicting the spec's own Open Questions

SPEC.md's Open Questions section is explicit: "Default platform-wide values for CAP-8's per-tenant ceilings... are unresolved... Needs a decision grounded in Flexi's own expected tenant profile before `bmad-build` implements concrete defaults." AD-9 nonetheless states flatly: "**100 tables/tenant, 50 columns/table**" with a one-line hedge ("conservative starting points, expected to be revisited"). That hedge doesn't resolve the tension — the spec was explicit that these numbers need to be *derived*, not asserted, and flagged the source research's illustrative figures as untraceable for exactly this reason. Fixing the divergence point (every implementer must use the same ceiling) is legitimate and good; picking the number without any derivation and presenting it as settled, when the driving spec explicitly called this out as unresolved and requiring justification, oversteps what the architecture altitude should decide unilaterally. This is a defensible place for architecture to make a call (a spine that left it "TBD" would itself be a finding), but it should be flagged as a assumption needing product/data sign-off, not stated as flatly as AD-1's Prisma-supersession rule.

**Fix:** Either (a) mark AD-9's numbers explicitly as "placeholder pending product decision, must be confirmed before CAP-1 implementation merges" rather than presenting them at the same confidence level as the rest of the AD, or (b) add one sentence on how 100/50 was derived (even "matches X comparable platform's free-tier ceiling" would satisfy the spec's "grounded, not copied from illustrative figures" bar) so it isn't just the same kind of unsourced guess the spec told bmad-build to avoid.

### M-2 — Operational/environmental envelope is covered only implicitly, and one piece (worker failure/retry policy) is genuinely silent

Deployment topology is covered (AD-8: in-process worker, same deploy unit as API). Config/env handling is covered (Consistency Conventions row, AD-8's `REDIS_URL` requirement, AD-4's `lock_timeout`). But the spine never states:
- **BullMQ job retry/backoff/dead-letter policy.** AD-4 says the worker "dequeues, `SET lock_timeout`, executes, and records the outcome" — but not what happens when a DDL job fails (lock timeout hit, Postgres error, worker crash mid-job). Does it retry? How many times, what backoff? Does a permanently-failed job leave the metadata row (written synchronously per CAP-1's "one transaction... with the Flexi metadata row") pointing at a table that was never actually created? This is exactly the kind of thing where one implementer might silently retry-forever and another might fail-and-orphan, producing genuinely divergent runtime behavior for the same failure case — it belongs in an AD, not left to the worker's `.spec.ts` to define ad hoc.
- **Worker observability / job status surfacing.** CAP-1's `202 Accepted` + job id implies a client needs to poll or be notified of completion/failure, but no AD or route in the Structural Seed defines a "get job status" endpoint or webhook. Without it, CAP-1's success criteria (physical DDL exists) is unverifiable by the caller — a real capability gap, not just a nicety.

**Fix:** Either add a short AD (or extend AD-4) covering: retry count/backoff for failed DDL jobs, what happens to the metadata row on terminal failure (rollback vs. mark-failed status), and a minimal job-status read path (e.g., `GET /api/tables/jobs/:jobId` or equivalent) — or explicitly move "DDL job failure handling and status polling" into Deferred with a stated interim behavior, so it's a conscious deferral rather than a silent gap.

### M-3 — CAP-4's cross-tenant relation rejection and CAP-3's "field-level error" shape aren't tied to an AD

CAP-4's success criterion includes "an attempt to link to a table outside the caller's tenant is rejected" — this is a real invariant (tenant-isolation-at-the-relation-field level) but no AD states *how* it's enforced or guarantees it structurally. AD-7 covers cardinality (many-to-one) but not tenant-scoping of the target. Given relation targets are resolved by table id (AD-6's pattern) and dynamic tables live one-per-tenant-schema with no cross-schema visibility by construction (per AD-1's schema isolation), this divergence may already be structurally impossible rather than needing an explicit check — but the spine should say so affirmatively (e.g., "structurally guaranteed because `forCurrentTenant()` only ever resolves within the caller's own schema — no explicit cross-tenant check needed") rather than leaving the reader to infer it. Right now a story-writer has to reconstruct this guarantee themselves from AD-1 + AD-3, and might instead add a redundant runtime tenant-id check that doesn't fit the "no tenant_id column on dynamic tables" model (Structural Seed's own note), or worse, skip validation because no AD called it out.

Similarly, CAP-3's "field-level error" response shape (which the frontend's CAP-7 must consume to "surface inline") isn't specified anywhere — not even a pointer to an existing convention. If it's meant to reuse an existing DTO-validation error envelope, name it; if not, this is a real frontend/backend contract gap.

**Fix:** One sentence under AD-7 or AD-1 making the cross-tenant relation guarantee explicit and structural (not a runtime check to remember). One sentence in Consistency Conventions naming the existing validation-error response shape CAP-3/CAP-7 must reuse.

## Low

### L-1 — `class-validator`-generated-at-runtime schemas are an unusual pattern; worth one more sentence on mechanism

AD-5 describes generating a "class-validator-compatible validation schema" from field definitions at runtime and caching it. `class-validator` is normally used with compile-time decorated classes, not dynamically synthesized ones — there are known patterns for this (e.g., building a validation-schema object and running it through `class-validator`'s functional API, or synthesizing a class at runtime via `class-transformer`), but the spine doesn't commit to which, leaving a real implementation-shaping decision to the story level. This isn't a divergence the spine strictly needs to close (both approaches satisfy CAP-3), but it's border-line enough (two implementers could pick meaningfully different runtime-codegen strategies with different performance/debuggability tradeoffs) that a one-line steer would help.

### L-2 — Migration-record retention/query surface undefined

CAP-5 requires migration records "for replay and audit" but the spine never states where these live (a metadata table alongside `TENANT_SCHEMA_METADATA_TABLE`? implied by the ERD's `MIGRATION_RECORD` box, but no column shape, no retention policy, no read API). Given cross-tenant replay tooling is explicitly deferred, this may be fine to leave thin — but "audit" implies someone can read these records, and no route/service method is named for that. Likely fine to leave for story-level design, flagging only because "audit" is a stated success criterion with no visible way to satisfy it.

### L-3 — Stack table doesn't pin BullMQ/ioredis versions

"latest stable at implementation time" is a reasonable call for new dependencies (avoids the spine going stale), but it's the one place in the Stack table without even a floor version, which is inconsistent with knex/pg's pinned versions just above it. Low risk since another reviewer is explicitly covering tech-currency verification, but worth a floor (e.g., "BullMQ v5.x line") so two implementers don't land on API-incompatible majors months apart.
