## Intent

**Problem:** After Story 2.1, the provisioning worker creates a `PROVISIONING` tenant but leaves it with no database schema and no bootstrap metadata tables (`_meta_tables`, `_meta_fields`, `_meta_migrations`). Every subsequent provisioning step and all dynamic-table functionality assumes the tenant schema already exists and is bootstrapped before activation.

**Approach:** Extend the provisioning service to continue after `tenant_creation` success by creating the tenant's PostgreSQL schema (`tenant_<Tenant.id>`) using an identifier-safe `CREATE SCHEMA IF NOT EXISTS`, then running the existing idempotent bootstrap migration (`ensureMetaTables`) inside a CLS-backed tenant context — recording `schema_created` and `bootstrap_migrated` step outcomes on the attempt and aborting safely on any failure.

## Boundaries & Constraints

**Always:** Resolve schema name via `resolveTenantSchema(tenantId)` — never string-interpolate manually. Create the schema via `knex.raw('CREATE SCHEMA IF NOT EXISTS ??', [schema])` (identifier binding `??`, not value binding `?`). Populate CLS context (`cls.runWith({ tenantId, schema }, ...)`) before calling any `TenantKnexService` method, following the `DdlWorker` pattern. Use `ensureMetaTables()` (existing idempotent method on `DynamicTablesService`) for the bootstrap step. Record `schema_created` and `bootstrap_migrated` step outcomes on the attempt. On any failure, record the failing step with a safe error code and re-throw — never activate the tenant in this story.

**Ask First:** Changing `ensureMetaTables()` implementation itself; adding non-metadata bootstrap tables; replacing `ensureMetaTables()` with a file-based `knex.migrate.latest()` approach; adjusting the 60-second provisioning job timeout budget.

**Never:** Use session-level `SET search_path`. Concatenate schema names from user-supplied input. Set `Tenant.status = ACTIVE` in this story. Call `TenantKnexService` outside a CLS `runWith` context. Record attempt status as `'failed'` — that is reserved for permanent failure in Story 2.6. Add setup links, email, First Admin, RBAC seeding, or audit finalization (those belong to Stories 2.3–2.6).

**Acceptance Criteria:**

- Given tenant creation has succeeded, when the provisioning service continues, then the schema name is resolved via `resolveTenantSchema(tenantId)` and passes the allowlist validator before any DB call.
- Given a valid tenant id, when `createTenantSchema` runs, then `CREATE SCHEMA IF NOT EXISTS tenant_<id>` executes inside a CLS-populated context and `schema_created` is recorded as `succeeded` on the attempt.
- Given the schema already exists (worker retry), when `createTenantSchema` runs again, then `CREATE SCHEMA IF NOT EXISTS` is a no-op with no error and `schema_created` is still recorded as `succeeded`.
- Given the schema exists, when `bootstrapTenantSchema` runs, then `ensureMetaTables()` creates `_meta_tables`, `_meta_fields`, and `_meta_migrations` inside `tenant_<id>` schema and `bootstrap_migrated` is recorded as `succeeded`.
- Given any schema or bootstrap step throws, when the error is caught, then the failing step is recorded with a safe error code (no stack trace, no raw SQL), the tenant remains `PROVISIONING`, attempt status is not changed to `'failed'`, and the error is re-thrown for BullMQ retry.
- Given a prior job timeout already marked the attempt `status: 'failed'` via `recordProvisioningTimeout()`, and a tenant is already linked to that attempt, when `startLifecycle()` resumes on BullMQ retry, then the attempt status is reset to `provisioning` before schema/bootstrap steps run, and `schema_created`/`bootstrap_migrated` are recorded as `succeeded` on the attempt rather than being silently dropped.

## Spec Change Log

### Iteration 1 (2026-08-22) — bad_spec: timeout-retry silently drops step outcomes

**Triggering finding:** Verification-gap review of the first implementation found that `provisioning.worker.ts`'s `withTimeout()` calls `recordProvisioningTimeout(attemptId)` on a 60s timeout, which sets the attempt's `status` to `'failed'` — but then still re-throws, so BullMQ retries the job. On retry, `startLifecycle()`'s `linkedTenant` resume path calls `recordTenantCreationSuccess()` / `provisionTenantSchema()` again, but every one of those writes goes through `updateAttemptSteps()`'s guard (`if (attempt.status === ATTEMPT_STATUS_FAILED && status !== ATTEMPT_STATUS_FAILED) return;`), which silently drops them because the attempt is already `'failed'`. This directly contradicts the frozen I/O matrix row "Worker retry — schema + tables already exist... both steps still recorded as `succeeded`" for the specific case where the previous attempt round ended in a timeout rather than a plain error throw.

**What was amended:** Added a Code Map entry and an Execution task instructing `startLifecycle()`'s `linkedTenant` resume branch to reset the attempt's `status` back to `provisioning` (via an empty-outcomes `updateAttemptSteps` call) before recording any further step outcomes, whenever it finds the attempt already `status: 'failed'` with a tenant already linked. Added a corresponding acceptance criterion and a mandatory second-invocation test case.

**Known-bad state avoided:** Do NOT modify the `updateAttemptSteps()` guard itself, and do NOT modify `recordProvisioningTimeout()` or the 60-second timeout budget — both are explicitly out of this story's scope (`Ask First` / reserved for Story 2.6 per the frozen Boundaries). The fix must live entirely in `startLifecycle()`'s resume path, conditioned on a tenant already being linked to the attempt (i.e. only a genuine in-flight resume, never a fresh dead attempt).

**KEEP instructions (preserve from the reverted first pass):** The overall structure was correct and should be re-derived unchanged: `provisionTenantSchema()` called OUTSIDE the `createOrResolveTenant()` try/catch so its errors propagate unreshaped; `createTenantSchema()` / `bootstrapTenantSchema()` each wrapping their own `cls.runWith()` call, recording `succeeded`/`failed` via `updateAttemptStep()`, and re-throwing on failure; `DynamicTablesModule` gaining `exports: [DynamicTablesService]` and `TenantsModule` importing it (no circular dependency — already verified clean); safe error codes (`SCHEMA_CREATION_FAILED`, `BOOTSTRAP_MIGRATION_FAILED`) with no stack trace or raw SQL in recorded messages. Only the resume-path status-reset logic is new.

## Design Notes

**`DynamicTablesService` injection strategy:** Before importing `DynamicTablesModule` into `TenantsModule`, verify `DynamicTablesModule` does not transitively import `TenantsModule` (circular). If clean, add `DynamicTablesModule` to `TenantsModule` imports and inject `DynamicTablesService` normally. If circular, extract `ensureMetaTables()` into a new `TenantSchemaService` placed in the `tenancy/` module (already global) to break the cycle — but only if the circular dependency is real.

**CLS context pattern** (mirror of `DdlWorker.process()` lines 141–147):

```typescript
const schema = resolveTenantSchema(tenantId);
await this.cls.runWith({ tenantId, schema }, async () => {
  await this.tenantKnexService.raw('CREATE SCHEMA IF NOT EXISTS ??', [schema]);
  await this.dynamicTablesService.ensureMetaTables();
});
```

**Step recording — no `running` state needed:** For schema/bootstrap steps, record directly as `succeeded` on success or `failed` on error. The `running` intermediate state is used only by `provisioning_start`. On failure, record the step and re-throw — do NOT catch-and-swallow or set attempt status to `'failed'` here.

**Resolve schema once per call site, not per DB operation:** `resolveTenantSchema(tenantId)` is deterministic and cheap — compute it once in `provisionTenantSchema()` (or once each in `createTenantSchema()`/`bootstrapTenantSchema()` is fine too) but do not call it more than once per step. Minor, non-blocking preference — do not let this drive additional abstraction.
