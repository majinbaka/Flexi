## Intent

**Historical problem (resolved):** The `auth` module was a stub returning `not-implemented`, and although `Role`/`Permission`/`RolePermission` tables already existed in the schema, nothing issued credentials or enforced them. The prior `User` model also hard-required a `tenantId`, which could not represent a platform-level Super Admin.

**Approach:** Split the actor model into three tables: `AuthAccount` (login identity only — `email` + `passwordHash`; the same email may back independent `AuthAccount` rows in different tenants, or as a `SystemUser`, each a wholly separate account), `SystemUser` (a platform-level actor, e.g. Super Admin, not scoped to any tenant), and `TenantUser` (a tenant-scoped actor — replaces today's flat `User`; both "Admin" and regular "User" are `TenantUser` rows, differing only by the `Role` assigned to them). Add password login issuing a short-lived JWT access token (carrying which actor type authenticated) plus a rotating refresh token (hashed at rest, tied to the `AuthAccount`), a `JwtAuthGuard`/`PermissionsGuard` pair other modules can adopt, and a seed script bootstrapping one demo tenant, one demo `TenantUser`, one demo `SystemUser`, and matching permissions/roles so the whole chain is verifiable end-to-end via a protected `GET /api/auth/me` that works for both actor types.

## Boundaries & Constraints

**Always:**

- `AuthAccount` holds identity only: `email`, `passwordHash`, `isActive`. `email` carries **no** DB-unique constraint by itself — the same address can back multiple independent `AuthAccount` rows (different tenants, or a `SystemUser` identity alongside separate `TenantUser` identities); each such row is a fully separate account with its own password. Disambiguation is per-scope, enforced at the **service layer** when an `AuthAccount` is created: no two `TenantUser`s in the same tenant may share an email, and no two `SystemUser`s may share an email. Never logged or returned in plaintext.
- `SystemUser` and `TenantUser` each link to at most one `AuthAccount` via `authAccountId`, and an `AuthAccount` may back at most one actor overall (`SystemUser` XOR `TenantUser`, never both). This 1-actor-per-account rule, and the "`TenantUser` belongs to exactly one tenant" rule, are enforced at the **service layer only** — no DB unique constraint on `authAccountId` — so relaxing either later (multi-tenant membership, a dual system+tenant actor) doesn't force an ERD migration.
- Refresh tokens stored only as a SHA-256 hash, keyed on `authAccountId`; the raw token is returned to the client once (login/refresh response) and never persisted in plaintext.
- Using a refresh token rotates it: the old row is marked `revokedAt` and a new one issued; replaying a revoked/expired/unknown token fails with 401 `INVALID_REFRESH_TOKEN`.
- `POST /api/auth/login` branches on whether `x-tenant-id` is present: **present** → resolve the `AuthAccount` whose `email` matches within a `TenantUser` of that tenant (tenant login); **absent** → resolve the `AuthAccount` whose `email` matches a `SystemUser` (system login). No separate endpoint or explicit "login type" field is needed — the header's presence/absence is the signal, since a client already knows which login surface (tenant vs platform) it's presenting.
- JWT access-token payload always carries `sub` (`authAccountId`) and `actorType` (`system` | `tenant`); a tenant token additionally carries `tenantId` + `tenantUserId`, a system token carries `systemUserId`; both carry the flattened permission codes granted through the actor's role(s) at issuance time.
- `SystemUser` is authorized through the exact same `PermissionsGuard` / Role→Permission mechanism as `TenantUser` — there is no `isSuperAdmin`-style bypass anywhere in the guard chain.
- `Permission.scope` is `SYSTEM` or `TENANT`. A `Role` with a `tenantId` set (a tenant role) can never hold a `SYSTEM`-scope permission — enforced wherever a `RolePermission` link is created (today: only the seed script, since RBAC admin CRUD is out of scope of this spec).
- `Role.tenantId` becomes nullable: `null` marks a system-level role (assignable only to a `SystemUser`), a set value marks a tenant-scoped role (assignable only to `TenantUser`s of that tenant). This mirrors the nullable-`tenantId` pattern the schema already uses on `LogEntry` for system-level rows.
- `GET /api/auth/me` serves both actor types from one route: it requires `auth.me.read` (`TENANT`-scope) when the caller is a `TenantUser`, and `system.me.read` (`SYSTEM`-scope) when the caller is a `SystemUser` — proving RBAC enforcement end-to-end on both sides of the split.
- `JwtAuthGuard`, `PermissionsGuard`, and `@RequirePermissions()` are reusable exports; this spec does not wire them onto any other module's stub controller.
- Passwords hashed with `bcryptjs` before storage/comparison; never logged or returned.

**Ask First:** None surfaced during investigation.

**Never:**

- No forgot/reset password flow (deferred — depends on the still-stub Mail & Template module).
- No RBAC admin management API (role/permission CRUD) — this spec only seeds and enforces. Consequently the "permission ceiling" rule (an actor assigning a role/permission to another can never grant more than it itself holds) has no live enforcement point yet, since there is no runtime role/permission-assignment endpoint — tracked in `deferred-work.md` for when that API is built.
- No OAuth/social login, no MFA, no cookie/session auth — bearer JWT only.
- No full multi-tenant isolation middleware (tracked separately in `deferred-work.md`) — tenant scoping here is limited to the `TenantUser`/`Role` lookups.
- No permission taxonomy for unbuilt feature modules — only `auth.me.read` (TENANT) and `system.me.read` (SYSTEM) are seeded.
- No guest-login endpoint (`POST /api/auth/guest`, unauthenticated account provisioning) — split out as an independently shippable follow-on, tracked in `deferred-work.md`.
- No multi-tenant membership, actor-switching, or workspace picker — an `AuthAccount` acts as exactly one `SystemUser` XOR one `TenantUser` in one tenant. This is an MVP scoping choice enforced in application code, not the schema, specifically so it can be lifted later without an ERD change.
- No impersonation (a `SystemUser` acting "as" a `TenantUser`) — deferred, tracked in `deferred-work.md`. The JWT claim name `impersonatedBy` is reserved (left undefined in the payload) so it's cheap to add later without a shape change.
- No emergency/break-glass "Root" actor distinct from `SystemUser` — decided against; `SystemUser` is the only, and sole, privileged actor. No open question here.
- No audit trail linking actions to `actorType`/`actorId` — `LogEntry` today has no actor fields at all; adding them is deferred to the Logging module, tracked in `deferred-work.md`.

## Design Notes

Permission codes are embedded in the JWT at login rather than re-queried per request: access tokens are short-lived (15m default), so the staleness window from a mid-session permission change is small, and this avoids a DB round trip on every guarded request. `PermissionsGuard` reads `request.user.permissions` (set by `JwtAuthGuard` from the decoded token), never the DB.

`Role.tenantId` is made nullable rather than introducing a parallel `SystemRole` table: the schema already uses this exact pattern on `LogEntry.tenantId` for system-level rows, so a `null`-means-system-scope convention is consistent with existing precedent rather than a new one. `SystemUser` and `TenantUser` themselves ARE split into separate tables (not a nullable-`tenantId` `User`) because that identity split is the actual point of this renegotiation — the JWT/login-resolution logic genuinely branches on which table a caller's `AuthAccount` maps to, whereas `Role` is a passive lookup table with no branching logic of its own.

`GET /api/auth/me` deliberately uses two different permission codes (`auth.me.read` vs `system.me.read`) rather than one shared code, so that `Permission.scope`'s enforcement rule (tenant roles can't hold `SYSTEM` permissions) never needs a carve-out — both actor types get a real, scope-correct permission to prove RBAC against, instead of one code awkwardly living on both sides of the scope boundary.

`AuthAccount.email` is deliberately left without a DB-unique constraint: the same email is expected to recur across different tenants (and independently as a `SystemUser`), each occurrence a fully separate account with its own password, matching the original schema's `[tenantId, email]` uniqueness pattern before the `AuthAccount`/`TenantUser` split. Because uniqueness now needs to be checked per-scope across two tables (`AuthAccount` + `TenantUser`, or `AuthAccount` + `SystemUser`) rather than one, it can't be a single `@@unique` — it's a service-layer check on account creation, consistent with this spec's other MVP-scoping rules. This is also why `x-tenant-id` returns as a required signal at login: with the same email potentially valid in several tenants, the header (or its absence, for system login) is what tells `login` which `AuthAccount` row to check the password against.
