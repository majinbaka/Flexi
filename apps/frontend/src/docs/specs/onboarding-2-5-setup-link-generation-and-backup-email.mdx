## Intent

**Problem:** After Story 2.4, the First Admin has a `pending_setup` `TenantUser` but no way to actually claim the account — no one-time setup secret is ever generated, and Ops has no backup delivery or regeneration path.

**Approach:** Add two sequential provisioning steps — a blocking `setup_link_generated` that creates a one-time, 24h-expiring setup token (SHA-256 hashed at rest, like `RefreshToken`) via a reusable `SetupLinkService`, and a non-blocking `setup_email_sent` that attempts a best-effort backup email (always recorded warning-only) — plus a permission-gated `POST /api/v1/super-admin/tenants/:id/setup-link` regeneration endpoint that calls the same service.

## Boundaries & Constraints

**Always:** New `SetupToken` model (public schema) mirrors `RefreshToken`: `id, tenantId, tokenHash @unique, expiresAt, revokedAt?, createdAt`. `SetupLinkService.generate(tenantId)` is the single source of truth for both the automatic step and manual regeneration: reject with `NotFoundException` if no `TenantUser` exists yet for the tenant (Story 2.4 must have run); otherwise, inside one `prisma.$transaction`, revoke (`revokedAt = now`) every non-revoked `SetupToken` for that tenant, generate a fresh raw token (`randomBytes(32).toString('base64url')`), hash it (`createHash('sha256').update(token).digest('hex')`, duplicated locally per `auth.service.ts:438-440` — do not cross-import `AuthModule`), set `expiresAt = now + 24h`, persist only the hash, and return the raw token + expiry in-memory once (it is never re-readable). `setup_link_generated` follows `assignFirstAdmin()`'s exact template (CLS `runWith`, try/succeeded/catch-log-failed-rethrow, error code `SETUP_LINK_GENERATION_FAILED`). `setup_email_sent` runs only after `setup_link_generated` succeeds, wraps `EmailDeliveryService.sendSetupInvite()` in its own try/catch that never rethrows, and records `succeeded`/`failed` without ever failing the outer provisioning call. The regeneration endpoint mirrors `checkSlugAvailability()`'s exact guard shape (`JwtAuthGuard`, `PermissionsGuard`, `@RequirePermissions(SYSTEM_TENANTS_ONBOARD_PERMISSION)`, `ActorType.SYSTEM` check) and returns `{ tenantId, setupToken, expiresAt }`.

**Ask First:** None outstanding — email-delivery strategy (stub, no real SMTP), response shape (raw token, no constructed URL), and regeneration behavior (always revoke-then-rotate) were resolved during clarification; see Design Notes.

**Never:** Add `nodemailer`/any real SMTP client or `SMTP_*` config — `EmailDeliveryService.sendSetupInvite()` always resolves `{ delivered: false, errorCode: 'SMTP_NOT_CONFIGURED' }`; real sending stays with the deferred Mail & Template module (`mail-templates.service.ts`, still a stub — do not wire it in). Build a `FRONTEND_URL`, a constructed setup URL, or any redemption/consumption route for the token — no story in Epic 2/3 owns that yet. Set `Tenant.status = ACTIVE` here (Story 2.6). Log the raw token anywhere — `stepOutcomes` JSON, `logger.*`, error messages — only safe metadata (`tenantId`, `expiresAt`).

## I/O & Edge-Case Matrix

| Scenario                               | Input / State                                                  | Expected Output / Behavior                                                                                  | Error Handling                                 |
| -------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| First run                              | First Admin assigned; no `SetupToken` exists                   | New `SetupToken` row (hashed); raw token returned once; `setup_link_generated` succeeded                    | —                                              |
| Full-job BullMQ retry                  | A `SetupToken` already exists from a prior run in this attempt | Prior token revoked, a brand-new token generated (raw value cannot be re-returned, so retry always rotates) | —                                              |
| No SMTP configured (always true today) | `setup_link_generated` succeeded                               | `setup_email_sent` recorded `failed` (`SMTP_NOT_CONFIGURED`)                                                | Never rethrown; provisioning continues         |
| No First Admin yet                     | Tenant has no `TenantUser`                                     | `NotFoundException`; step recorded `failed`                                                                 | Safe error code, no stack trace, no email      |
| Manual regeneration                    | Permitted SystemUser calls `POST .../setup-link`               | Prior token(s) revoked; new token + `expiresAt` returned                                                    | 403 if actor isn't `SYSTEM` / lacks permission |

**Acceptance Criteria:**

- Given required provisioning steps have succeeded, when setup link generation runs, then Flexi generates a one-time setup token expiring in 24 hours, and no plaintext token value is ever persisted to `stepOutcomes`, logs, or the database.
- Given setup link generation succeeds, when backup email delivery fails (as it always does today, with no SMTP configured), then tenant activation semantics are unaffected and the outcome is recorded warning-only on `setup_email_sent` without logging the plaintext token.
- Given a permitted SystemUser calls `POST /api/v1/super-admin/tenants/:id/setup-link`, then the request is gated by `system.tenants.onboard`, any prior unexpired `SetupToken` for that tenant is revoked, and a new token + expiry is returned.
- Given a tenant with no `TenantUser` yet, when setup link generation is attempted, then it fails with a safe error code and no token is created.

## Design Notes

**Why every invocation rotates the token:** the raw token is never persisted (only its hash), so a BullMQ full-job retry cannot "re-return" a previously issued token — it must mint a new one and revoke the old. This matches the human's decision that manual regeneration always rotates, and today it's inconsequential either way since backup email always fails (`SMTP_NOT_CONFIGURED`).

**Why no real SMTP client:** the Mail & Template module (SMTP config, template editor) is tracked as its own deferred, independently-shippable module (`deferred-work.md`). Building a working `nodemailer` integration here would silently absorb that module's scope. `EmailDeliveryService` is written so a future story can swap its body for a real send without touching the provisioning orchestration or its step-outcome contract.

**Setup link vs. raw token (resolved ambiguity):** an earlier deferred-work entry flagged a conflict between PRD/UX "Setup Link" language and an older spec's raw `setupToken` field. This story returns the raw token only (no constructed URL) — no frontend route exists yet to redeem it, so inventing a `FRONTEND_URL` convention now would be speculative.
