## Intent

**Problem:** Story 1.3 persists an idempotency key on accepted onboarding attempts, but repeated valid submits still create duplicate attempts and the form still stops after slug recheck instead of calling the durable submit API. Network retries and double submits can therefore confuse Ops and downstream provisioning.

**Approach:** Make `POST /api/v1/super-admin/tenants` idempotent by binding each idempotency key to the normalized safe payload, returning the existing attempt for matching retries, and returning a safe conflict with the existing attempt id for mismatched payload reuse. Wire the onboarding form to submit the real API with a stable per-intent idempotency key and visible created/retry/conflict feedback.

## Boundaries & Constraints

**Always:** Enforce the existing `JwtAuthGuard`, `PermissionsGuard`, `system.tenants.onboard`, and System actor boundary before any attempt lookup or creation. Normalize payload before comparison. Return or resume an existing matching attempt before checking whether its slug now exists, so safe retries are not broken by later provisioning. Preserve safe response shapes only: attempt ids, normalized metadata, request/idempotency identity, and operational status copy.

**Ask First:** Adding an attempt detail route, creating Tenant/AuthAccount/TenantUser/Role/schema/setup-token state, changing auth token claims, or introducing a frontend test framework.

**Never:** Do not compare raw request bodies, persist secrets, expose raw SQL/stack traces, treat different-payload idempotency reuse as success, or rely on a service-only pre-check without database protection against concurrent duplicate keys.

## I/O & Edge-Case Matrix

| Scenario              | Input / State                                                                                                     | Expected Output / Behavior                                                                                                                            | Error Handling                                                                                  |
| --------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| First accepted submit | Permitted SystemUser posts valid normalized payload with new idempotency key                                      | One onboarding attempt is created and returned with `accepted` status                                                                                 | No Tenant, account, role, schema, setup token, or audit state is created                        |
| Matching retry        | Same actor or permitted SystemUser posts the same idempotency key with the same normalized safe payload           | Existing attempt is returned; no new attempt is inserted; UI shows an idempotent retry notice with the attempt id                                     | Slug recheck must not reject this replay merely because provisioning may later consume the slug |
| Conflicting reuse     | Same idempotency key is posted with materially different normalized tenant name, slug, plan, or First Admin email | No new attempt is inserted; API returns 409 with `IDEMPOTENCY_CONFLICT` and existing attempt id when available; UI shows a form-level conflict notice | Do not leak the existing payload or unsafe request details                                      |
| Concurrent duplicate  | Two valid requests with the same key race                                                                         | Exactly one attempt wins; the loser returns the winning attempt if payload matches or conflict if payload differs                                     | Raw unique-constraint/database errors are translated to safe API responses                      |

**Acceptance Criteria:**

- Given a permitted SystemUser submits a valid onboarding payload with a new idempotency key, when the POST endpoint succeeds, then exactly one accepted onboarding attempt is persisted and returned.
- Given the same idempotency key and matching normalized payload are submitted again, when the POST endpoint handles the retry, then the existing attempt is returned and no duplicate attempt is created.
- Given the same idempotency key is reused with different normalized payload, when the POST endpoint handles the request, then it returns a safe 409 idempotency conflict with the existing attempt id when available and creates no state.
- Given an operator submits the onboarding form, when creation succeeds, replays, conflicts, or fails, then the UI presents the correct form-level state without losing the stable idempotency key for the in-flight submission.

## Spec Change Log

## Design Notes

Treat idempotency comparison as a comparison of normalized `safePayload`, not raw body or request identity. Header `Idempotency-Key` remains preferred over body key; the UI should send the header and may omit the body key. A returned existing attempt can be the same DTO shape plus replay metadata; a conflict should reveal only a code/message and `existingAttemptId`.
