# Epic 1 Context: Safe Tenant Onboarding Intake

{/* Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. */}

## Goal

Epic 1 lets permitted internal operators start tenant onboarding safely by submitting validated tenant, plan, and First Admin identity data through the Super Admin surface. It replaces manual engineer setup entry points with a permission-gated, preflight-validated, durable, idempotent intake flow that can hand off accepted attempts to later provisioning without creating duplicate tenant, account, role, or schema records.

## Stories

- Story 1.1: Permission-Gated Onboarding Entry And Form Shell
- Story 1.2: Field Validation And Slug Preflight
- Story 1.3: Durable Permission-Gated Attempt API
- Story 1.4: Idempotent Submission Handling

## Requirements & Constraints

- Only authenticated `SystemUser` actors with `system.tenants.onboard` may access tenant onboarding creation. Tenant-scoped actors, unauthenticated actors, and SystemUsers without that permission must fail before tenant or attempt state is created.
- The onboarding form captures only Phase 1 intake data needed for provisioning and tracking: tenant name, desired slug/subdomain, selected plan, and First Admin email.
- Input validation must run before provisioning state exists. Required tenant name, plan, and First Admin email are rejected when missing; invalid email and invalid slug/subdomain formats are rejected; duplicate slug/subdomain requests are rejected.
- Slug availability is a preflight UX state, but the backend must repeat the availability validation during submit before creating any durable state.
- Accepted submissions create a stable Onboarding Attempt with actor identity, safe payload metadata, request identity, idempotency identity, timestamps, status, and step outcomes.
- Repeating the same request with the same idempotency identity and matching payload returns or resumes the existing attempt outcome. It must not create duplicate Tenant, First Admin, role assignment, or tenant schema records.
- Reusing an idempotency identity with materially different payload must return an explicit conflict error and, when available, expose the existing attempt id to the UI.
- Plan is Phase 1 metadata for display and tracking. It does not need to enforce entitlements or feature flags in this epic.
- Audit and attempt records must avoid plaintext passwords, plaintext setup tokens, secret values, stack traces, and raw SQL. Errors should expose safe operational detail only.
- Tenant availability remains controlled by later provisioning. `PROVISIONING`, `FAILED`, and `SUSPENDED` tenants must not be presented as login-ready or usable by tenant-scoped surfaces.

## Technical Decisions

- The authoritative submit endpoint for this epic is `POST /api/v1/super-admin/tenants`; it must enforce `system.tenants.onboard` before any state creation.
- Use the existing auth and permission stack rather than introducing a separate Super Admin bypass. The permission boundary is explicit capability-based access, not a broad role shortcut.
- Durable attempt reservation is part of intake and precedes asynchronous provisioning. Long-running schema creation, bootstrap migration replay, First Admin creation, role assignment, setup-link generation, activation, and failure compensation belong to later epics.
- Idempotency must bind request identity to a safe payload comparison so network retries are safe while conflicting payload reuse is rejected.
- Tenant schema naming and schema creation are downstream concerns, but intake must preserve enough safe identifiers for later provisioning to use the approved `tenant_<Tenant.id CUID>` convention and must never trust client input as a schema name.
- Schema-per-tenant and dynamic-table planning constrain later provisioning: tenant-schema access should use Knex schema scoping, not session-level `SET search_path`, and dynamic-table metadata/data belongs in tenant schemas through the DynamicTables owner module. Epic 1 should not add direct tenant-schema DDL or dynamic-table access paths.
- Migration replay remains the default provisioning strategy until measured thresholds justify revisiting template schema cloning. Intake must not move heavy schema work into the synchronous request path.
- Error handling should preserve enough safe state for operators and engineers to trace accepted attempts without exposing secrets.

## UX & Interaction Patterns

- Reuse the existing authenticated Flexi admin shell and components such as `Layout`, `Sidebar`, `TopNav`, `PageHeader`, `Button`, `Input`, `Select`, `Card`, `Table`, `Badge`, and `Icon`.
- The Tenants list is the entry surface. `Onboard New Tenant` is a page-level primary action, not a separate sidebar item.
- Users without `system.tenants.onboard` do not see create controls; direct route access shows a permission screen or redirect and creates no onboarding state.
- The onboarding form is one operational flow with grouped sections for Tenant identity, First Admin, Plan/options, and Preflight. Submit stays disabled until required fields are valid and slug availability is known.
- Slug preflight uses visible checking, available, and conflict states. A conflict should produce a field-level error and may offer an alternate generated slug.
- Submit pending disables mutating controls and shows that an onboarding attempt is being created until an attempt id is returned.
- Idempotent retry detection should show a clear notice and route the operator to the existing attempt instead of implying a second submission was created.
- Copy and status text should be concrete and operational. Machine identifiers such as ids, slugs, idempotency keys, URLs, schema names, and setup-token snippets use monospace styling where shown.
- Creation UX is optimized for desktop/laptop operations, while responsive views must still support status review and clear failure/success interpretation.

## Cross-Story Dependencies

- Permission gating is foundational: form access, preflight, submit, attempt reservation, and idempotent retry handling all depend on the same `system.tenants.onboard` boundary.
- Field validation and slug preflight must be complete before the durable attempt API accepts a request; otherwise invalid or duplicate input could become persistent state.
- Idempotent submission handling depends on the durable attempt model storing request identity, payload comparison data, and attempt status consistently.
- Later provisioning epics depend on Epic 1 producing exactly one accepted attempt per idempotent request and preserving enough safe metadata for status, audit, and failure review.
