## Intent

**Problem:** After Story 2.5, `provisionTenantSchema()` stops at `sendBackupEmail()` — no step ever sets `Tenant.status = ACTIVE`, no compensation runs on failure, and no permanent audit record exists. A tenant that finishes every step successfully is stuck in `PROVISIONING` forever, and a failure anywhere leaves whatever partial state was created with only ephemeral `stepOutcomes` on the attempt row.

**Approach:** Add a final blocking `activation` step that flips `Tenant.status = ACTIVE` only after all six prior steps succeeded, plus an `audit_finalized` step that always runs (success or failure) and persists one permanent `TenantOnboardingAuditLog` row. On failure of any step 1-6, run best-effort compensation per the Compensation Matrix in `failure-modes.md`, transition `Tenant.status = FAILED` (or leave attempt `failed-needs-manual-cleanup` if compensation itself fails), and record compensation outcome in the audit row.

## Boundaries & Constraints

**Always:** New `TenantOnboardingAuditLog` model (public schema, mirrors `LogEntry`'s field-typing conventions): `id String @id @default(uuid())` (sibling of `TenantOnboardingAttempt`, not `LogEntry`'s cuid), `attemptId String @unique`, `tenantId String?`, `actorIdentity Json`, `requestIdentity Json`, `safePayload Json`, `stepOutcomes Json`, `compensation Json?`, `finalStatus String`, `createdAt DateTime @default(now())`; `@@index([tenantId])`, `@@index([finalStatus])`, `@@map("tenant_onboarding_audit_logs")`. Never updated or deleted after insert (append-only per `failure-modes.md` Invariants). `activation` step: only runs after `sendBackupEmail()` completes (regardless of its outcome, since it's non-blocking); sets `Tenant.status = 'ACTIVE'` via `prisma.tenant.update`; records step outcome with `tenantId`/`tenantSlug`/`tenantStatus: 'ACTIVE'`. `audit_finalized` step: always the last action in `provisionTenantSchema()`'s success path and in every catch-driven failure path; writes the `TenantOnboardingAuditLog` row using `prisma.tenantOnboardingAuditLog.upsert` keyed on `attemptId` (idempotent against full-job BullMQ retry — a retry after an already-finalized audit must not throw a unique-constraint error). On any step-1-through-6 failure: catch at the `provisionTenantSchema()` orchestrator level (not inside each step, which still self-record and rethrow per existing pattern), run compensation per the Compensation Matrix (`failure-modes.md`) for whichever steps actually succeeded, set `Tenant.status = 'FAILED'` unless compensation itself fails, then call the same `audit_finalized` write with `finalStatus` reflecting `'failed'` or `'failed-needs-manual-cleanup'` and a populated `compensation` field. Compensation attempts, in reverse order of what succeeded: revoke `SetupToken` rows (`revokedAt = now`), deactivate/delete the `TenantUser` and its `AuthAccount` and `Role`, drop the tenant schema (`DROP SCHEMA IF EXISTS ?? CASCADE` through `TenantKnexService`, identifier-bound like `createTenantSchema()`), leave the `Tenant` row (never delete — `Tenant.status = 'FAILED'` is the terminal state, not row removal). If any compensation sub-step throws, catch it, continue attempting the remaining sub-steps, and mark `finalStatus = 'failed-needs-manual-cleanup'` with every known identifier (tenant id, schema name, AuthAccount id, TenantUser id, role id, failed compensation step) in the audit `compensation` field — never let a compensation failure crash the job uncaught. Extend `TenantOnboardingStepName` with `'activation' | 'audit_finalized'`, and `TenantOnboardingAttemptStatus` with a terminal success value (`'succeeded'`) and `'failed-needs-manual-cleanup'`. Audit payload fields are the same safe/redacted set already used in `stepOutcomes` today — no raw setup token, no password, no stack trace, no raw SQL ever enters `TenantOnboardingAuditLog`.

**Ask First:** None outstanding — the compensation matrix, audit schema shape, and manual-cleanup threshold are fully specified in `failure-modes.md` (loaded as context) and SPEC.md CAP-6/CAP-7.

**Never:** Delete the `Tenant` row as compensation (only `FAILED` status). Delete or mutate a `TenantOnboardingAuditLog` row after insert. Persist a raw setup token, password, stack trace, or raw SQL anywhere in the audit row. Build a `GET /status` endpoint or any UI (Epic 3's scope). Attempt schema-drop compensation for a schema that was never confirmed created (only drop when `schema_created` succeeded).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| All 6 steps succeeded | `sendBackupEmail()` returned (any outcome) | `Tenant.status = ACTIVE`; `activation` succeeded; `audit_finalized` succeeded with `finalStatus: 'succeeded'` | — |
| Step 1-5 fails (e.g. `bootstrap_seeded`) | Schema created, seed step throws | Compensation drops schema (since `schema_created` succeeded), `Tenant.status = FAILED`, audit records failed step + compensation outcome | Rethrow suppressed at orchestrator catch; job still fails for BullMQ retry visibility after audit write completes |
| Compensation sub-step itself throws | e.g. schema drop fails mid-cleanup | Remaining compensation sub-steps still attempted; `finalStatus = 'failed-needs-manual-cleanup'`; audit lists every known identifier and the failed compensation step | Never rethrown past `audit_finalized` |
| Full-job BullMQ retry after activation already succeeded | `Tenant.status` already `ACTIVE`, audit row already exists for `attemptId` | `activation` step is a safe no-op (status already `ACTIVE`); `audit_finalized` upserts the same row without duplicate-key error | — |
| Full-job BullMQ retry after failure+compensation already ran | `Tenant.status` already `FAILED`, audit row exists | Re-running steps 1-6 either re-fails fast (schema absent) or is idempotent per existing step contracts; orchestrator catch re-runs compensation (idempotent: revoke/deactivate/drop are all already-gone-is-fine) and re-upserts the same audit row | — |

**Acceptance Criteria:**
- Given every required provisioning step succeeds, when activation runs, then `Tenant.status` becomes `ACTIVE` and `TenantOnboardingAuditLog` records success with safe resource identifiers.
- Given any required step fails or times out, when the attempt reaches a final failure outcome, then `Tenant.status` is not `ACTIVE`, and the audit/attempt record captures the failed step, final failure state, compensation status per step, and known identifiers (tenant id, schema name, AuthAccount id, TenantUser id, role id, failed compensation step) where available.
- Given an accepted attempt succeeds or fails, when audit finalization runs, then exactly one permanent `TenantOnboardingAuditLog` row is persisted for that `attemptId` (never duplicated on retry), excluding plaintext passwords, plaintext setup tokens, and secrets.

## Design Notes

**Why `audit_finalized` upserts on `attemptId` instead of insert-once:** a full-job BullMQ retry re-enters `provisionTenantSchema()` from the top (per Story 2.5's documented resume semantics); if `activation` already succeeded and set `ACTIVE`, a retry must not crash on a duplicate-key insert for the audit row -- upsert keeps the write idempotent without changing the append-only *content* guarantee (the row's terminal content is the same on every write once the attempt is truly final).

**Why compensation lives in the orchestrator's catch, not per-step:** each of the 6 existing steps already self-records and rethrows on its own failure (existing pattern, unchanged). Compensation needs to know *which* steps actually succeeded to know what to clean up -- that's only knowable one level up, after catching the rethrown error, by reading back the attempt's current `stepOutcomes`.
