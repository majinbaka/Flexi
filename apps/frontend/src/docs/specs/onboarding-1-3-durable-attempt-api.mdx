## Intent

**Problem:** Story 1.2 validates tenant onboarding input but still cannot record an accepted request. Ops needs a permission-gated API that persists a durable attempt only after authentication, actor-type, permission, payload validation, and slug availability checks pass.

**Approach:** Implement `POST /api/v1/super-admin/tenants` as the Story 1.3 intake boundary. The endpoint creates exactly one durable onboarding attempt record with actor identity, safe payload metadata, request identity, idempotency identity, timestamps, an initial accepted status, and initial step outcomes, without creating tenants, accounts, roles, schemas, setup tokens, or audit logs yet.

## Boundaries & Constraints

**Always:** Enforce `JwtAuthGuard`, `PermissionsGuard`, `system.tenants.onboard`, and `ActorType.SYSTEM` before service persistence. Reuse shared onboarding validation and slug format rules. Repeat tenant slug availability before creating an attempt. Store only safe payload metadata: tenant name, normalized slug, plan, and normalized First Admin email. Capture request identity and idempotency identity from headers/body in a stable, non-secret shape.

**Ask First:** Adding Tenant lifecycle/status fields, creating Tenant rows, implementing retry/idempotency conflict semantics beyond storing the idempotency identity, provisioning schemas, creating First Admin accounts, introducing audit log tables, or changing auth token claims.

**Never:** Do not allow unauthenticated, tenant-scoped, or unpermitted callers to create attempts. Do not persist plaintext passwords, setup tokens, authorization headers, cookies, raw stack traces, or raw SQL. Do not move provisioning work into the synchronous request path.

## I/O & Edge-Case Matrix

| Scenario           | Input / State                                                                                    | Expected Output / Behavior                                                                                                                                           | Error Handling                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Accepted attempt   | Permitted SystemUser posts valid tenant name, slug, plan, First Admin email, and idempotency key | Response returns a durable attempt id, normalized safe payload, actor identity, request identity, idempotency identity, `accepted` status, and initial step outcomes | No Tenant, AuthAccount, TenantUser, Role, tenant schema, setup token, or audit row is created  |
| Unauthorized actor | Missing token, tenant token, or SystemUser token without `system.tenants.onboard`                | Request fails before service attempt creation                                                                                                                        | 401 or 403 envelope; service persistence is not called for controller-level tenant actor block |
| Invalid payload    | Required fields missing, invalid email/slug, or missing/unknown plan                             | Request fails before attempt creation                                                                                                                                | 400 validation envelope with safe field codes                                                  |
| Duplicate slug     | Valid payload requests an existing `Tenant.slug`                                                 | Request fails before attempt creation                                                                                                                                | 409 conflict envelope without exposing existing tenant details                                 |

## Spec Change Log

## Design Notes

Story 1.3 stores the idempotency identity but does not enforce replay semantics; Story 1.4 owns matching-payload retry and conflicting-payload reuse behavior. The attempt status can be a string literal in Prisma, matching existing project practice for evolving status fields. Initial step outcomes should record only intake-local facts such as permission check, validation, slug availability, and attempt reservation.

Use request identity as a safe operational summary, not a raw header dump. Accept an explicit `Idempotency-Key` header and optionally a body `idempotencyKey`, preferring the header when both are present; reject missing identity so Story 1.4 has a durable key to build on.

Prisma client generation exited successfully in this workspace but did not expose a new `tenantOnboardingAttempt` delegate. Keep the Prisma model and migration as the source schema, but use parameterized raw SQL for Story 1.3 persistence until client generation is repaired or refreshed in a follow-up.
