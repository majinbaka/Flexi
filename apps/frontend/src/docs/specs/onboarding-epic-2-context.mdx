# Epic 2 Context: Tenant Provisioning To Active Workspace

{/* Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. */}

## Goal

Flexi can take an accepted onboarding attempt and turn it into a usable tenant workspace through an asynchronous, auditable provisioning workflow. The epic owns the product-visible commit boundary: a tenant starts unavailable in `PROVISIONING`, receives its schema, bootstrap data, First Admin identity, Tenant Admin assignment, setup delivery path, and permanent audit evidence, and becomes `ACTIVE` only after every required step succeeds. Failures and timeouts must remain explicit, safe to inspect, and unable to appear as successful provisioning.

## Stories

- Story 2.1: Provisioning Worker And Tenant Lifecycle Start
- Story 2.2: Tenant Schema Provisioning And Bootstrap Migration
- Story 2.3: Bootstrap Defaults And Tenant RBAC Seed
- Story 2.4: First Admin Identity And Tenant Admin Assignment
- Story 2.5: Setup Link Generation And Backup Email Outcome
- Story 2.6: Activation Boundary, Failure Recording, And Permanent Audit

## Requirements & Constraints

Provisioning must run outside the synchronous web request path, advancing through explicit step outcomes with success, failure, and timeout recorded rather than hidden behind a long-running request.

A tenant record is created once and begins with `Tenant.status = PROVISIONING`. Tenant-scoped login and application routes must reject `PROVISIONING`, `FAILED`, and `SUSPENDED`; only `ACTIVE` is usable or handoff-ready.

Tenant schema creation uses the `tenant_<Tenant.id CUID>` naming convention. Required bootstrap migrations must complete before activation; schema failures record the failed step and safe error detail.

Bootstrap data required before activation: system settings (locale, timezone, base currency, config flags); default workflow statuses `Draft`, `In Review`, `Active`, `Archived`; roles Admin/Tenant Admin, Manager, Member with the default permission matrix (Admin full CRUD plus role/config/audit control; Manager read-only settings with soft-delete-level business-object access; Member own-record access only); default categories `General`, `Operations`, `Administrative`; and notification templates `WELCOME_SETUP_INVITE`, `PASSWORD_RESET_REQUEST`, `WORKSPACE_LIMIT_WARNING`.

The First Admin is exactly one login identity and exactly one `TenantUser`, starts in `pending_setup`, and is never backed by a `SystemUser`. The tenant-scoped `TENANT_ADMIN` / `Tenant Administrator` role must exist and be assigned to the First Admin before activation, with tenant-scope-only permissions (`Role.tenantId` = new tenant id).

Setup link generation happens only after required steps succeed: one-time, 24-hour expiration unless a stricter policy applies, plaintext token never persisted anywhere. Regeneration is `POST /api/v1/super-admin/tenants/:id/setup-link`, gated by `system.tenants.onboard` for MVP.

Backup email delivery is warning-only across all plans once the UI setup link is generated successfully — SMTP failure never changes activation semantics and is recorded without logging the plaintext token (UI shows `Email Delivery Failed (Copy Link Manually)`).

Every accepted attempt, success or failure, produces permanent `TenantOnboardingAuditLog` evidence: actor, request identity, safe payload metadata, step outcomes, compensation status, final status, safe resource identifiers. Excludes plaintext passwords/tokens, secrets, stack traces, raw SQL. `failed-needs-manual-cleanup` applies only when automated compensation can't safely continue; failure records include known identifiers (tenant id, schema name, AuthAccount id, TenantUser id, role id, failed compensation step) when available.

Successful provisioning targets under 1 minute (p95 under 30 seconds). Attempts exceeding 1 minute transition to timeout/failure rather than spin indefinitely. Migration replay stays the default strategy until p95 latency exceeds 30 seconds or tenant migration files exceed 50, at which point template schema cloning should be evaluated.

## Technical Decisions

Schema-per-tenant isolation is binding. Onboarding owns/coordinates tenant schema provisioning because tenant-scoped and dynamic-table functionality assumes the schema already exists (the Dynamic Table Builder module explicitly defers schema provisioning as out of its own scope).

Tenant identity must come only from a verified source, never client-supplied strings. Schema names resolve through a server-side resolver validated against an identifier allowlist (`/^[A-Za-z_][\w$]*$/`, `NAMEDATALEN`-capped), never concatenated from client input; unit tests should cover adversarial inputs, not just the happy path.

Tenant-schema queries use Knex `.withSchema(schema)` at the call site through one shared pool (never per-tenant pools). No session-level `SET search_path` anywhere — under transaction-mode pooling it can leak across tenants on connection reuse. Raw DDL SQL, if unavoidable, scopes transaction-locally inside an explicit transaction.

Migration replay must not rely on Knex `schemaName` alone — it only relocates the tracking table, not the DDL target. Each migration must get its schema via `withUserParams({ schema })` and call `.withSchema(schema)` itself. Tests should assert objects land in the tenant schema (via `information_schema.tables`), not `public`. One tenant's migration failure must not abort others in batch runs.

Per-step outcomes must be captured so activation makes one final decision, retaining known identifiers (tenant id, schema name, auth account id, TenantUser id, role id, failed compensation step) for escalation.

Dynamic table metadata/data live inside each tenant schema via Knex, not Prisma. Tenant schemas must support pinned `_meta_tables`, `_meta_fields`, `_meta_migrations` tables for the Dynamic Table Builder, created lazily by that module on first use — onboarding doesn't create them but must not produce a schema incompatible with them.

Dynamic-table guardrails live on public-schema `Tenant.dynamicTableGuardrails` (nullable, platform defaults 100 tables/tenant, 50 columns/table) rather than tenant-schema metadata, since they're needed before a tenant's first table exists; onboarding leaves this field at its nullable default.

## UX & Interaction Patterns

Operator-facing step vocabulary: checking permission, reserving onboarding attempt, creating tenant record, provisioning tenant schema, preparing Tenant Admin role, creating first admin account, assigning Tenant Admin role, activating tenant, finalizing audit. Step labels shown to Ops should mirror these names.

Setup handoff (tenant URL, setup link, first admin email, tenant id, schema name where safe) shows only when `Tenant.status = ACTIVE`. If a token-bearing link can't be safely re-read after reload, show safe metadata plus a regeneration path rather than exposing or inventing the secret.

Failure states hide customer handoff controls and show the failed step, safe error detail, compensation state (completed/partial/manual-cleanup-required), and safe identifiers when available. Status uses text plus badges/icons, not color alone; step changes announce via a polite live region. Error copy names the field/step, consequence, and next action — never stack traces, raw SQL, plaintext tokens, or generic "unknown error" text.

## Cross-Story Dependencies

Depends on Epic 1 for an accepted, permission-gated, durable, idempotent Onboarding Attempt with safe payload metadata and actor/request identity; replays must not duplicate tenants, schemas, First Admin identities, roles, or role assignments.

Provisioning order is sequential at the activation boundary: tenant creation before schema provisioning; schema provisioning before bootstrap seeding; bootstrap state before First Admin creation and Tenant Admin assignment; setup link generation after required success; activation and audit finalization close the workflow.

Epic 3 depends on this epic's step names, statuses, safe identifiers, setup link availability, warning-only email outcome, and audit records to render progress, handoff, and failure review without adding remediation controls in Phase 1.
