## Intent

**Problem:** Stories 1-2 let a tenant admin create tables and edit fields via the DDL queue, but nothing lets any caller read or write the _rows_ of a dynamic table — there is no DML route, and no per-table validation exists to reject bad writes before they hit Postgres.

**Approach:** Add `rows.controller.ts` (`/api/tables/:tableId/rows` + `/:rowId`, AD-6) backed by new synchronous DML methods on `DynamicTablesService` (AD-2) that read/write rows via `TenantKnexService.forCurrentTenant()` directly — never the BullMQ queue (AD-4's DML exemption). Add a validation-schema generator that builds a class-validator-compatible schema from a table's `_meta_fields` rows, cached in-memory per table id, invalidated synchronously whenever Story 2's `enqueueFieldEdit()` accepts a change (AD-5).

## Boundaries & Constraints

**Always:** All row DML goes through `DynamicTablesService` only — no other module or code path calls `TenantKnexService` for dynamic-table rows (AD-2). Every write validates against the field-derived schema (required, `dataType` type-check, and `config`'s `minLength`/`maxLength` for STRING/TEXT, `min`/`max` for NUMBER, `enum` for SELECT) before touching the DB; a failure returns the existing class-validator-style field-error array via `BadRequestException`, matching `HttpExceptionFilter`'s envelope — no new error shape. The validation schema is generated once per table (on first row-route access, lazily) and rebuilt synchronously inside `enqueueFieldEdit()` after a successful validation, before the job is enqueued — never rebuilt per DML request. Cache is in-memory, keyed by `tableId`, per-backend-instance (AD-5 — no Redis). `tableId` resolves through `_meta_tables` (never trusted as a literal table name) and the resolved physical table name is used only as a parameterized Knex `.table()` call, never string-concatenated into raw SQL. Routes use `@UseGuards(JwtAuthGuard, PermissionsGuard)` + `@RequirePermissions('dynamic-tables.rows.<action>')`, matching `tables.controller.ts`'s pattern. Row responses include `id`, every field's current value, `created_at`, `updated_at`.

**Ask First:** none anticipated — DML surface and validation approach are fully pinned by AD-2/AD-5/AD-6.

**Never:** Do not build CAP-4 relation fields or resolve `RELATION`-typed columns (Story 4 — no such fields exist yet, `NON_RELATION_FIELD_DATA_TYPES` still applies). Do not add `Tenant.dynamicTableGuardrails` enforcement (Story 5). Do not build the frontend (Story 6). Do not add row-count/page-size/rate-limit guardrails — unresolved per SPEC.md's Open Questions, out of this story's scope. Do not touch the BullMQ queue for any row operation.

## I/O & Edge-Case Matrix

| Scenario                                 | Input / State                                                                   | Expected Output / Behavior                                                 | Error Handling                                            |
| ---------------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------- |
| Create row, valid                        | POST with all required fields present, correct types                            | `201` + created row (id, fields, timestamps)                               | N/A                                                       |
| Create row, missing required field       | POST omitting a `required: true` field                                          | Rejected before DB write                                                   | `400`, field-error array naming the missing field         |
| Create row, constraint violation         | POST with STRING over `config.maxLength`, or SELECT value outside `config.enum` | Rejected before DB write                                                   | `400`, field-error array naming the field + violated rule |
| Create row, unknown table id             | POST to `:tableId` with no matching `_meta_tables` row                          | N/A                                                                        | `404`, same shape as Story 2's unknown-table error        |
| List rows                                | GET `/api/tables/:tableId/rows`                                                 | `200` + array of rows                                                      | N/A                                                       |
| Get one row, unknown id                  | GET `/:rowId` not present in the physical table                                 | N/A                                                                        | `404`                                                     |
| Update row, valid partial                | PATCH `/:rowId` with a subset of fields                                         | `200` + updated row; only cache-validated fields checked                   | N/A                                                       |
| Update row, cache stale after field edit | PATCH right after a Story-2 field edit added a new required field               | Validated against the _rebuilt_ schema (post-edit), not a stale cached one | `400` if the new required field is missing                |
| Delete row                               | DELETE `/:rowId`                                                                | `204`                                                                      | N/A                                                       |

**Acceptance Criteria:**

- Given a valid row payload for an existing table, when POSTed, then the response is `201` with the created row including `id`/`created_at`/`updated_at`.
- Given a row payload missing a required field, when POSTed, then the response is `400` with a field-error array naming the missing field, and no row is written.
- Given a row payload violating a field's `config` constraint (length/range/enum), when POSTed, then the response is `400` naming the violated field/rule, and no row is written.
- Given a table whose fields were just edited via Story 2's `PATCH /api/tables/:tableId/fields`, when a row is subsequently written, then validation runs against the rebuilt schema (post-edit), not a stale cached one.
- Given an unknown `tableId` or `rowId`, when any row route is called, then the response is `404` in the same shape as Story 2's unknown-table error.

## Design Notes

`validateRowPayload()` builds its field-error strings as `"<fieldSlug>: <reason>"` (e.g. `"email: must not exceed 255 characters"`), collected into an array and thrown as `new BadRequestException({ message: errors, error: 'VALIDATION_ERROR' })` — `HttpExceptionFilter` already joins an array `message` into `error.message`, so this reuses the existing envelope path without new filter logic. Constraint keys read from `_meta_fields.config` (`minLength`, `maxLength`, `min`, `max`, `enum`) are optional — a field with no matching `config` key skips that check, only `dataType`+`required` are always checked.
