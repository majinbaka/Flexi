## Intent

**Problem:** Stories 1-3 let a tenant admin create tables, edit fields, and read/write rows, but `FieldDataType.RELATION` is rejected everywhere it's checked (`ddl-worker.ts`'s `addTypedColumn`, DTOs' `NON_RELATION_FIELD_DATA_TYPES` allowlist, `checkFieldType`'s validation) — there is no way to link one dynamic table's rows to another's.

**Approach:** Extend Story 2's field-edit path (`PATCH /api/tables/:tableId/fields`) to accept a `RELATION` field naming a `relatedTableId`, materialized as a literal Postgres FOREIGN KEY column (AD-7) via the existing DDL queue. Extend Story 3's `listRows`/`getRow` to detect RELATION-typed fields in a table's schema and resolve them via a server-side `leftJoin` + `json_agg`, never N+1 per-row queries.

## Boundaries & Constraints

**Always:** A relation field's target table is validated to exist (via `findMetaTableOrThrow`) before the field-edit job is enqueued, returning the same 404 shape as an unknown `tableId`. The FK column DDL uses a schema-qualified `.inTable()` value (the caller's own current tenant schema, from `resolveTenantSchema`/`TenancyClsStore`) — never a bare unqualified table name — so cross-tenant linking is structurally impossible by construction (AD-7), not an application-layer check. The FK's `onDelete` behavior is `SET NULL` (relation column is nullable unless `required: true`); `onUpdate` is not set (`_meta_tables` ids are immutable). `_meta_fields.relation_target_table_id` (already present per AD-10) is populated on a relation field's `upsert-field` metadata effect. `listRows`/`getRow` resolve every RELATION field on the table via one `leftJoin` + `json_agg` per relation, still through `TenantKnexService.forCurrentTenant()` only (AD-2) — never a second round-trip per row. A relation field's DML value is the target row's `id` (or `null`); Postgres's own FK constraint is the sole enforcer of referential integrity at write time (no service-layer existence re-check duplicating it). Row responses embed a resolved relation as `{ id, ...targetRowFields }` under the field's slug (`null` when unset), alongside the existing raw FK-id column.

**Ask First:** none anticipated — FK mechanics, cardinality (many-to-one only), and `json_agg` approach are fully pinned by AD-7/CAP-4.

**Never:** Do not support many-to-many or one-to-many (Story 4 is many-to-one only, per SPEC.md's CAP-4 decision). Do not add an application-layer "same tenant" check as primary defense against cross-tenant linking — schema-qualification is the only defense; an app-layer check is at most redundant. Do not resolve nested/transitive relations (a relation field's target row is embedded flat, one level deep only). Do not touch guardrails (Story 5) or the frontend (Story 6). Do not allow a `modify` edit to change an existing field's `dataType` to or from `RELATION` — reject it synchronously (400, no job enqueued) before it can reach the destructive expand/contract path; converting a live column to/from an FK is out of scope (removing and re-adding the field is the supported workaround).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Add relation field, valid target | `PATCH .../fields` edit with `dataType: RELATION`, `relatedTableId` pointing at an existing table in the same tenant | Field-edit job enqueued; FK column added via DDL queue; `_meta_fields.relation_target_table_id` set | N/A |
| Add relation field, unknown target | `relatedTableId` with no matching `_meta_tables` row | N/A | `404`, same shape as an unknown `tableId` |
| Add relation field, missing `relatedTableId` | `dataType: RELATION` with no `relatedTableId` | N/A | `400`, field-error naming the missing property |
| Create row with valid relation value | POST with the relation field set to an existing target row's `id` | `201`; FK constraint accepts the write | N/A |
| Create row with dangling relation value | POST with the relation field set to a non-existent target row `id` | N/A | `400`/DB constraint violation surfaced as a field-error (Postgres FK violation caught and reshaped, not a raw 500) |
| List rows with a relation field | GET `/api/tables/:tableId/rows` on a table with one RELATION field | `200`; each row's relation slug holds the joined target row (or `null`), via one `leftJoin` + `json_agg`, not per-row queries | N/A |
| Delete a target row referenced by a relation | DELETE the target row while source rows still reference it | Source rows' relation column is set to `null` (`ON DELETE SET NULL`) | N/A |
| Modify existing field to/from RELATION | `PATCH .../fields` edit with `operation: 'modify'` and `dataType: RELATION` (or an existing RELATION field's `dataType` changed to something else) | N/A | `400` before any DDL job is enqueued, field-error stating this conversion is unsupported |
| Update row with dangling relation value | PATCH `/:rowId` setting a RELATION field to a non-existent target row `id` | N/A | `400`, same reshaped field-error envelope as the create-row case (Postgres FK violation caught, not a raw 500) |

**Acceptance Criteria:**
- Given a field-edit adding a `RELATION` field with a valid `relatedTableId` in the same tenant, when the job completes, then the physical table gets an FK column referencing the target table, schema-qualified to the caller's own tenant schema.
- Given a `relatedTableId` with no matching `_meta_tables` row, when the field-edit is submitted, then the response is `404` before any DDL job is enqueued.
- Given a table with a resolved `RELATION` field, when its rows are listed or fetched, then each row includes the joined target row under the field's slug, produced by exactly one additional query (`leftJoin`/`json_agg`), not one query per row.
- Given a target row deleted while still referenced, when the referencing row is subsequently read, then its relation field resolves to `null` (FK's `ON DELETE SET NULL` applied).
- Given a `modify` edit attempting to change a field's `dataType` to or from `RELATION`, when the PATCH is submitted, then the response is `400` before any DDL job is enqueued.
- Given a row update (`PATCH .../rows/:rowId`) setting a RELATION field to a non-existent target row `id`, when the Postgres FK constraint rejects the write, then the response is `400` with the same reshaped field-error envelope `createRow` uses, not a raw `500`.

## Spec Change Log

- **Finding:** Review (loop 1) surfaced an intent gap: the frozen spec never addressed what happens when a `modify` field-edit changes an existing field's `dataType` to/from `RELATION` — it silently fell into the destructive expand/contract path and failed late, inside the async DDL worker, instead of synchronously.
  **Amended:** Added an explicit `Never` boundary rule and two new I/O matrix rows (modify-to/from-RELATION rejected; update-row FK-violation reshaping) requiring synchronous 400 rejection before job enqueue. Human confirmed: forbid the conversion outright (removing and re-adding the field is the supported workaround) rather than supporting it like `add`.
  **Known-bad state avoided:** A `modify` edit silently accepted at the API boundary, enqueued, and only failing deep inside the BullMQ worker after retries — a confusing, hard-to-diagnose failure mode instead of a clear synchronous validation error.
  **KEEP:** All six previously-completed tasks (DTO changes, `FieldEditStep`/`FieldMetadataEffect` types, `add` branch of `buildFieldEditSteps`, `ddl-worker.ts`'s `add-relation-column` DDL, validation-schema/`checkFieldType` relation support, `listRows`/`getRow`'s `leftJoin`+`json_agg` resolution) were correct as implemented and must survive re-derivation unchanged in approach — only the `modify` branch's missing guard and `updateRow`'s missing FK-violation reshaping (a related, lower-severity `patch`-classified finding bundled into this same loopback since it touches the same acceptance criteria) are new work.

## Design Notes

`FK onDelete = SET NULL` (not RESTRICT or CASCADE) was chosen because CAP-4 has no stated requirement to block target-row deletion, and CASCADE would silently delete unrelated rows across tables -- SET NULL is the least-surprising default and keeps the relation field's own `required` validation (checked at write time, not enforced by the DB) as the mechanism for "this relation must be set," consistent with how every other field's `required` is app-validated rather than DB-enforced (AD-5/Story 3 precedent).

`relatedTableId` lives as a first-class DTO property (not folded into the untyped `config` bag) because it drives DDL (which table to `.inTable()`) and metadata (`_meta_fields.relation_target_table_id`) -- both are structural, not a per-field validation constraint like `minLength`/`enum`, so it doesn't belong in `config`.
