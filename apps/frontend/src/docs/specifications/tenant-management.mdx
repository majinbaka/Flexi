# Quản lý và onboarding tenant

## Mục đích và quyền truy cập

`/tenants` hiển thị inventory tenant có lọc/phân trang. System user có cả
actor type `system` và permission `system.tenants.onboard` thấy nút tạo mới;
`/tenants/onboard` cũng tự hiển thị Permission Denied nếu thiếu một trong hai
điều kiện. Backend bảo vệ toàn bộ API v1 trong flow này bằng JWT, permission
cùng tên và kiểm tra System actor ở những thao tác onboarding.

## Danh sách tenant

Màn hình tải `GET /api/v1/super-admin/tenants`, cancel request cũ khi filter
hoặc trang thay đổi, và chỉ nhận response mới nhất. Có trạng thái loading,
lỗi tải, inventory rỗng và không tìm thấy theo filter.

## Onboarding flow

1. Người dùng nhập tên tenant, slug, email First Admin và plan. Trường Notes
   có trên UI nhưng không nằm trong request gửi API.
2. UI dùng shared validation, sau 450 ms kiểm tra slug hợp lệ qua
   `GET .../slug-availability`; chỉ cho submit khi slug có sẵn.
3. Submit tạo một idempotency key an toàn, giữ lại key đó nếu payload chưa
   đổi, rồi gửi `POST /api/v1/super-admin/tenants` với header
   `Idempotency-Key`.
4. API xác thực payload/key, actor còn active và slug; tạo attempt `accepted`,
   enqueue BullMQ provisioning job, rồi trả `202` attempt. Một key cùng
   payload trả replay của attempt; key cùng payload khác trả conflict.
5. Worker tạo tenant/schema/metadata/default data/First Admin/setup token,
   thử gửi invite, rồi activation. Attempt và audit lưu outcome theo step.

## Kết quả và giới hạn hiện tại

UI công bố attempt tạo mới, replay hoặc conflict (kèm attempt ID nếu API trả)
và lỗi slug/generic. Nó không poll trạng thái provisioning hay hiển thị audit.

`EmailDeliveryService` khởi tạo transporter khi `SMTP_ENABLED=true`; chỉ khi
cờ này tắt (hoặc thiếu `SMTP_FROM`) nó mới trả `SMTP_NOT_CONFIGURED` mà không
gửi gì. Khi bật, lỗi được map thành `SMTP_AUTH_FAILED`, `SMTP_TIMEOUT`,
`SMTP_RECIPIENT_REJECTED` hoặc `SMTP_DELIVERY_FAILED`; recipient bị từ chối
trong response cũng tính là không gửi được. Provisioning ghi outcome cho bước
gửi setup invite trong mọi trường hợp.

API có endpoint tạo lại setup link (`POST .../tenants/:id/setup-link`), trả
raw token đúng lần gọi đó và revoke token setup chưa revoke trước đó. Token
được đổi qua `POST /api/v1/setup/redeem` (public) và frontend đã có route
`/setup-account` đọc `?token=` để First Admin đặt mật khẩu đầu tiên.
