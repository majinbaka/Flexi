# Collaboration & Governance

## Trạng thái specification gate

<Badge tone="warning">Target specification — chưa được triển khai đầy đủ</Badge>

Trang này chuẩn hóa yêu cầu stakeholder cho phân hệ **Collaboration &
Governance**. Các actor, API `/api/v1`, entity, state machine và policy bên dưới
là contract mục tiêu/backlog; chúng không mô tả một module đang hoạt động trong
implementation hiện tại.

Đối chiếu ngày **2026-08-26** cho thấy backend chưa có module Application,
Change Request, Resource Comment, Dependency Graph, Governance Policy hoặc
Break-glass. Pages và Workflows mới trả trạng thái `not-implemented`. Dynamic
Tables đã có tenant scope, JWT guard và permission guard nhưng chưa có
`version_hash`/optimistic locking theo contract này.

## 3. Functional requirements

### MVP — nhóm nhỏ

- Mỗi Resource thuộc đúng một Application và lưu `created_by`.
- Mọi lần lưu sử dụng `version_hash` để phát hiện ghi đồng thời.
- Comment đơn cấp có thể gắn vào Resource hoặc vị trí bên trong Resource, ví
  dụ Workflow Node hay Page Component.
- App Owner có thể chuyển ownership cho user khác trong cùng Tenant.

### Production-ready

- Một Change Request gom thay đổi của nhiều loại Resource để kiểm thử và phê
  duyệt đồng bộ.
- Impact analysis quét dependency trước khi submit và chỉ ra breaking change.
- Audit diff so sánh Live với Draft theo JSON Patch RFC 6902.
- Resource có thể archive và restore trong retention window mặc định 30 ngày.

### Enterprise governance

- Strict Separation of Duties ngăn người tạo tự approve/publish và tách vai trò
  approve khỏi publish.
- Break-glass cho phép bypass có kiểm soát khi xảy ra P1 Incident.
- Template dùng chung có lifecycle `DRAFT → APPROVED → DEPRECATED → ARCHIVED`.
- Policy engine chặn publish khi sai naming convention, lộ secret hoặc thiếu
  RBAC bắt buộc.
- System Admin chỉ truy cập tenant qua ticket có TTL và immutable audit.
- Audit Trail có thể xuất sang S3/GCS để lưu trữ dài hạn.

## 7. Lifecycle và luồng xử lý

### Change Request

```text
[DRAFT] --Submit--> [SUBMITTED] --Approve--> [APPROVED] --Publish--> [PUBLISHING]
                         |                        |                         |
                         +--Reject--> [REJECTED] +--failure--------------> [FAILED]
                                                                          |
                                                        success-----------+--> [PUBLISHED]
```

Luồng resubmit từ `REJECTED` và semantics rollback từ `FAILED` chưa được xác
nhận. Implementation phải chốt transition hợp lệ trước khi tạo state machine.

### Optimistic locking

```text
[UNLOCKED] --Maker edits--> [OPTIMISTIC CHECK]
                                  |
                   hash match ----+---- hash mismatch
                        |                     |
                        v                     v
                [SAVED + NEW HASH]      [409 CONFLICT]
```

### Break-glass

```text
[INACTIVE] --Request + MFA--> [ACTIVE, TTL 2h]
                                      |
                             expire or revoke
                                      v
                            [EXPIRED / TERMINATED]
```

## 9. Security và tenant isolation

- `tenant_id` phải lấy từ auth context đã xác thực, không tin giá trị do client
  gửi trong body/query.
- Mọi data access phải tenant-scoped; lựa chọn RLS hay schema-per-tenant cho các
  entity governance là quyết định kiến trúc chưa được chốt.
- AuditLog, `CRItem.diff_patch` và `ResourceComment` phải qua redactor trước khi
  persist và trước khi render/export.
- Admin token toàn cục không được query trực tiếp tenant data. Cross-tenant
  access cần ticket, MFA/OTP, TTL, scoped identity và audit riêng.
- Audit export phải bảo toàn tenant boundary, encryption, integrity và retention.

Current implementation có tenant ownership trên một số control-plane model và
JWT/permission guard cho Dynamic Tables. PostgreSQL RLS, governance redactor,
scoped impersonation và immutable audit export chưa được xác nhận.

## 11. Acceptance criteria mục tiêu

### AC-01 — Chặn Maker tự phê duyệt

- **Given** Strict SoD bật trên Sales App và User A tạo `CR-101`.
- **When** User A gọi endpoint approve trong lúc CR ở `SUBMITTED`.
- **Then** API trả `403 ERR_SOD_VIOLATION`, CR giữ nguyên và security audit được
  ghi.

### AC-02 — Phát hiện ghi đồng thời

- **Given** Maker A và B cùng mở Page X tại `hash_v1`.
- **When** A lưu thành `hash_v2`, sau đó B gửi lệnh lưu với `hash_v1`.
- **Then** API trả `409 ERR_OPTIMISTIC_LOCK_CONFLICT`, payload chứa dữ liệu mới
  nhất ở `hash_v2` và UI đưa Maker B vào manual merge flow.

### AC-03 — Publish qua break-glass

- **Given** Production có P1 Incident, Operator C có permission và flow chuẩn bị
  nghẽn.
- **When** C kích hoạt break-glass với `INC-9911`, MFA hợp lệ rồi publish CR.
- **Then** CR được publish, audit mang `is_breakglass: true`, mọi action mang
  nhãn `[BREAK-GLASS]` và Tenant Alert nhận cảnh báo khẩn cấp.
