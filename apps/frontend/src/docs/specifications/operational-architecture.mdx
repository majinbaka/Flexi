# Quy cách kiến trúc vận hành

## Trạng thái specification gate

Trang này ghi lại **kiến trúc vận hành mục tiêu do stakeholder cung cấp** cho
nền tảng Flexi. Các API, mô hình triển khai và tiêu chuẩn vận hành bên dưới là
yêu cầu/định hướng kiến trúc; chúng không mặc nhiên đại diện cho hành vi đã
được triển khai trong production.

## 1. Mục tiêu và phạm vi

### Mục tiêu

Định nghĩa toàn bộ thông số kiến trúc vận hành (Operational Architecture
Specification) cho nền tảng low-code Flexi, chuyển đổi từ mô hình thử nghiệm
(Docker Compose single-node) sang hệ thống enterprise-ready đáp ứng khả năng
mở rộng, độ sẵn sàng cao, cách ly tenant tuyệt đối và an toàn dữ liệu.

### Phạm vi

- Kiến trúc hệ thống xung quanh REST API (NestJS), React/Vite, PostgreSQL
  (schema-per-tenant), Redis và Queue/Worker.
- Toàn bộ 24 tiêu chuẩn vận hành: từ HA, Scaling, Stateless, Zero-downtime,
  Migration, Rate Limiting, DR/RPO/RTO đến Data Residency, Canary rollout và
  Secret Rotation.
- Phân tầng yêu cầu cho ba cấp độ triển khai: Single-Node Production, HA
  Production và Enterprise Deployment.

---

## 2. Actors và permissions

- **Platform Super Admin**: Quản trị toàn bộ hạ tầng, cấp phát tenant, cấu hình
  quota, thực hiện migration toàn hệ thống và giám sát SLO/SLI.
- **Tenant Admin**: Quản trị cấu hình trong phạm vi tenant (Pages, Workflows,
  Users, Dynamic Tables), yêu cầu export/delete dữ liệu tenant.
- **Tenant Developer/Configurator**: Tạo schema động (Dynamic Tables), quy
  trình (Workflows), giao diện (Pages), cấu hình Mail/i18n.
- **Tenant End-User**: Người dùng cuối thao tác trên ứng dụng do Flexi sinh ra,
  chịu ràng buộc bởi RBAC của tenant.
- **Automated System/Worker**: Daemon thực hiện Cron Jobs, Queue Processing,
  Schema Provisioning và Backup tasks.

## 3. Functional requirements

- **Cấp phát và quản lý Schema Tenant**: Tự động tạo PostgreSQL schema riêng
  (`tenant_<tenant_id>`) và queue cách ly khi onboarding.
- **Dynamic Table và Versioning**: Cho phép chỉnh sửa bảng/trường động mà không
  làm sập ứng dụng; ghi lại lịch sử phiên bản cấu hình (schema versioning).
- **Stateless API Executions**: Xử lý request từ NestJS mà không lưu session
  state local; lưu session/token blacklist trên Redis.
- **Bảo vệ Secret và Redaction**: Tự động lọc (redact) các trường nhạy cảm (JWT
  secret, DB password, API keys) khỏi log, audit trail và response API.
- **Zero-Downtime Deployment**: Cập nhật mã nguồn nền tảng mà không ngắt kết
  nối của các tenant đang hoạt động.
- **Tenant Data Export và Deletion**: Xuất toàn bộ dữ liệu/cấu hình của một
  tenant thành gói nén mã hóa; xóa sạch toàn bộ schema và dữ liệu liên quan,
  tuân thủ cam kết GDPR/Privacy.

---

## 4. Business rules

- **Cách ly tuyệt đối (Strict Isolation)**: Request của Tenant A không bao giờ
  được truy cập schema hoặc Redis key-space của Tenant B.
- **Giới hạn tài nguyên (Tenant Quotas)**: Mỗi tenant bị giới hạn bởi số
  request/phút (Rate Limit), lưu trữ tối đa (Storage Quota) và số lượng worker
  concurrency tối đa.
- **Không đảo ngược không kiểm soát (Migration Safety)**: Mọi thao tác DDL trên
  Dynamic Tables phải tạo `backupRestorePoint` và có tập kịch bản rollback
  tương ứng trước khi áp dụng.
- **Xác thực JWT và Context Injection**: Mỗi request hợp lệ phải chứa
  `tenant_id` trong JWT payload. Service context phải validate `tenant_id` với
  kết nối DB trước khi thực thi query.

## 5. Entity/data model ở mức khái niệm

- **Platform Tenant**: `id`, `code`, `status` (ACTIVE, SUSPENDED, PURGED),
  `db_schema_name`, `tier` (FREE, PRO, ENTERPRISE), `created_at`.
- **Tenant Quota & Limits**: `tenant_id`, `max_storage_mb`, `max_api_rpm`,
  `max_concurrent_workers`, `max_dynamic_tables`.
- **Schema Migration Log**: `id`, `tenant_id`, `version`, `ddl_script`, `status`
  (PENDING, APPLIED, FAILED, ROLLED_BACK), `execution_time_ms`, `applied_at`.
- **Audit Trail**: `id`, `tenant_id`, `actor_id`, `action`, `resource`,
  `payload_redacted` (JSONB), `ip_address`, `timestamp`.
- **Secret Vault Reference**: `id`, `tenant_id`, `secret_key_name`,
  `vault_path`, `version`, `last_rotated_at`.

## 6. API capability (contract-level)

- `POST /api/v1/admin/tenants` — Onboarding tenant mới, kích hoạt provisioning
  worker.
- `GET /api/v1/admin/tenants/{tenant_id}/health` — Lấy trạng thái sức khỏe hạ
  tầng riêng của tenant.
- `POST /api/v1/admin/tenants/{tenant_id}/migrations` — Chạy cập nhật schema cho
  một hoặc tất cả tenant.
- `POST /api/v1/admin/tenants/{tenant_id}/export` — Yêu cầu đóng gói dữ liệu
  tenant (trả về async job ID).
- `DELETE /api/v1/admin/tenants/{tenant_id}/data` — Lệnh xóa vĩnh viễn dữ liệu
  tenant (yêu cầu xác nhận hai lớp).
- `GET /health/liveness` — Endpoint kiểm tra tiến trình ứng dụng đang sống.
- `GET /health/readiness` — Endpoint kiểm tra khả năng kết nối tới PostgreSQL,
  Redis và Queue.

## 7. Lifecycle/state machine

### Tenant Provisioning & Migration State Machine

```text
CREATED -> PROVISIONING -> ACTIVE

ACTIVE -> MIGRATING -> ACTIVE
                    -> ROLLBACK_IN_PROGRESS -> DEGRADED

ACTIVE -> SUSPENDED -> EXPORTING -> PENDING_PURGE -> PURGED
```

- Migration thành công đưa tenant từ `MIGRATING` về `ACTIVE`.
- Migration thất bại đưa tenant qua `ROLLBACK_IN_PROGRESS` đến `DEGRADED`.

## 8. Validation và error cases

- **Tenant Isolation Breach Failure**: Request chứa `tenant_id` không khớp với
  JWT context → trả về HTTP `403 Forbidden`, đồng thời kích hoạt cảnh báo an
  ninh.
- **Rate Limit Exceeded**: Tenant vượt quá giới hạn request/phút → trả về HTTP
  `429 Too Many Requests` kèm header `Retry-After`.
- **Dynamic DDL Conflict**: Người dùng cập nhật trường động làm đứt gãy ràng
  buộc khóa ngoại hoặc kiểu dữ liệu → trả về HTTP `400 Bad Request` kèm thông
  điệp lỗi chi tiết đã loại bỏ thông tin hệ thống nhạy cảm.
- **Dependency Failure (Redis/DB Down)**: Readiness probe thất bại → trả về HTTP
  `503 Service Unavailable`, gỡ pod/instance khỏi Load Balancer.

---

## 9. Security và tenant isolation

- **Data Isolation**: Áp dụng mô hình schema-per-tenant trên PostgreSQL. Mọi kết
  nối từ API Pool phải thực hiện `SET search_path TO tenant_x, public;` trước
  khi gửi query.
- **Queue Isolation**: Định tuyến job theo queue name
  `queue:{tenant_id}:{module_name}`.
- **Redaction Policy**: Mọi module log (Winston/Pino) đi qua middleware tự động
  quét regex để loại bỏ các key `password`, `token`, `secret`, `credit_card`,
  `private_key`.
- **Encryption**: Mã hóa TLS 1.3 in-transit cho toàn bộ giao tiếp API, Redis và
  DB. Mã hóa AES-256 Envelope Encryption at-rest cho cơ sở dữ liệu và Object
  Storage.

---

## 10. Audit/observability

- **Log Structure**: Format JSON chuẩn hóa chứa `trace_id`, `tenant_id`,
  `actor_id`, `component`, `severity`, `message`, `context_redacted`.
- **Metrics**: Đẩy metric theo định dạng OpenTelemetry/Prometheus:
  `http_requests_total{tenant_id, status}`,
  `db_connection_pool_usage{tenant_id}`, `queue_lag{tenant_id, queue_name}`.
- **Tracing**: Đính kèm W3C TraceContext vào mọi REST request và BullMQ Job để
  trace xuyên suốt Frontend → NestJS → Queue → Worker → PostgreSQL.

## 11. Acceptance criteria (Given/When/Then)

### Scenario 1: Cách ly dữ liệu khi truy vấn REST API

- **Given** User A thuộc Tenant 1 có JWT token hợp lệ.
- **When** User A gửi request `GET /api/v1/dynamic-tables/orders/data`.
- **Then** Hệ thống chỉ thực thi query trên schema `tenant_1` và không trả về
  bất kỳ bản ghi nào thuộc `tenant_2`.

### Scenario 2: Zero-downtime deployment khi có schema migration

- **Given** Hệ thống đang chạy ở phiên bản V1 với 1.000 request/giây.
- **When** Deploy phiên bản V2 yêu cầu thêm column mới vào DB.
- **Then** Migration áp dụng phương pháp non-breaking DDL (Expand-Contract),
  không có request nào bị lỗi 5xx trong suốt quá trình rollout.

## 12. Dependencies

- **Runtime**: Node.js v20 LTS, NestJS v10+.
- **Databases & Cache**: PostgreSQL 16+, Redis 7+ (cluster mode cho HA).
- **Storage & Queue**: S3-compatible Object Storage (MinIO/AWS S3), BullMQ.
- **Orchestration**: Docker, Kubernetes, Ingress NGINX/Envoy Proxy.

## 13. Quyết định còn mở

### Chiến lược Schema Scale Limit

Schema-per-tenant trên PostgreSQL gặp giới hạn hiệu năng khi số lượng tenant
vượt mốc 2.000 schemas/instance do RAM overhead của catalog cache.

- **Trade-off**: Giữ schema-per-tenant giúp cách ly tuyệt đối nhưng cần chuyển
  sang Multi-DB Instance khi scale.
- **Stakeholder action**: Cần xác nhận định hướng nhóm khách hàng (B2B SME số
  lượng lớn hay B2B Enterprise số lượng vừa).

### Mức độ linh hoạt của Dynamic DDL Rollback

Cần quyết định có hỗ trợ tự động rollback dữ liệu khi người dùng xóa cột động
(Drop Column) hay không.

- **Trade-off**: Tự động khôi phục tốn dung lượng storage backup rất lớn; không
  hỗ trợ làm tăng nguy cơ mất dữ liệu người dùng.

## 16. Phân tích chi tiết thiết kế chuyên sâu

### Chiến lược Dynamic Tables và DDL Lock Removal

- **Thách thức**: Khi người dùng tạo/sửa bảng động trên Flexi, thao tác
  `ALTER TABLE` có thể gây `AccessExclusiveLock`, làm nghẽn toàn bộ kết nối của
  tenant đó.
- **Giải pháp Enterprise**: Mọi thao tác đổi tên trường/xóa trường động không
  chạy DDL trực tiếp. Flexi đánh dấu Logical Delete trong metadata engine và
  dùng PostgreSQL Views để map cột. Việc dọn dẹp DDL vật lý chỉ diễn ra ngầm
  trong Maintenance Window.

### Cơ chế Secret Redaction tại layer Observability

- **Giải pháp**: Xây dựng `SafeLogger` wrapper tại NestJS Core. Trước khi JSON
  log được đẩy ra `stdout` hoặc OpenTelemetry Collector, một tập regex thay thế
  chuỗi nhạy cảm bằng `[REDACTED]`. Cơ chế này bảo đảm credential của tenant
  không bị lộ ngay cả khi log đi ra hệ thống giám sát bên ngoài.
