## Actor và phân quyền mục tiêu

SRS định nghĩa ba actor. Authorization hiện tại không có cơ chế
`isSuperAdmin` bypass: cả System user và Tenant user đều phải có toàn bộ
permission gắn trên endpoint. `TENANT_ADMIN` chỉ được tạo cho First Admin khi
onboarding; `END_USER` chưa phải role code trong public RBAC model.

## Yêu cầu mục tiêu

### Quota người dùng

`Used seats` phải đếm user ở `ACTIVE`, `PENDING_INVITE`,
`PENDING_APPROVAL` và cả `LOCKED`; user `DELETED` cùng invite
`EXPIRED`/`REVOKED` không chiếm seat. Giá trị `max_users = -1` nghĩa là không
giới hạn.

**Điểm cần xác nhận:** công thức literal trong SRS chỉ liệt kê `ACTIVE`,
`PENDING_INVITE`, `PENDING_APPROVAL`, nhưng ghi chú kế tiếp yêu cầu `LOCKED`
vẫn chiếm quota. Trang này ưu tiên diễn giải từ ghi chú; implementation cần
chốt lại rule trước khi mã hóa.

### Mời và tạo người dùng

Invite mục tiêu nhận danh sách email cùng role, kiểm tra quota, tạo token an
toàn có hạn 72 giờ, tạo user `PENDING_INVITE`, rồi gửi link
`/accept-invite?token=…`. Redeem token hợp lệ nhận Full Name, Password và
Confirm Password; transaction cập nhật mật khẩu, user sang `ACTIVE` và invite
sang `USED`.

- Resend phải làm token cũ hết hiệu lực, tạo token/hạn mới và gửi lại email.
- Revoke phải chuyển invite sang `REVOKED`, user sang `DELETED` và giải phóng
  quota ngay.
- Email phải unique trong cùng tenant; trùng email trả
  `409 EMAIL_ALREADY_EXISTS`.

Implementation hiện tại chỉ có flow tương tự cho **First Admin**: onboarding
tạo `AuthAccount` + `TenantUser(pending_setup)`, phát setup token hash-only có
hạn **24 giờ**, và `/setup-account` nhận Password/Confirm Password. Đây không
phải invite user chung, không nhận Full Name và không triển khai resend/revoke
theo trạng thái trong SRS.

### Xóa và chuyển giao dữ liệu

Soft delete mục tiêu đổi user sang `DELETED`, vô hiệu session/token và giải
phóng quota. Hard delete chỉ xóa ngay khi user không sở hữu dữ liệu; nếu có,
admin phải chọn target user cùng tenant, khác source và đang `ACTIVE`. Chuyển
owner, ghi audit `DATA_TRANSFERRED` và xóa source phải nằm trong một
transaction. Admin tự xóa mình trả `400 CANNOT_DELETE_SELF`; target sai trả
`400 INVALID_TARGET_USER`.

Repository chưa có ownership contract chung cho các bảng động, endpoint xóa
user, revoke toàn bộ session khi xóa, hay persistence cho audit event này.

### Switch tenant và impersonation

Theo SRS, System Admin chọn tenant bằng `X-Tenant-Id`, sau đó có thể nhận JWT
impersonation tối đa 15 phút với `impersonator_id` và cờ impersonated. UI phải
hiển thị banner đỏ cố định, cho phép thoát để khôi phục session System Admin;
start/hoạt động trong session đều phải được audit.

`AccessTokenPayload` hiện chỉ dành trước field `impersonatedBy` nhưng không
bao giờ gán. Tenant login hiện chọn tenant bằng header `x-tenant-id`; chưa có
middleware System Admin switch tenant, token impersonation, audit hay banner.

## Luồng đã triển khai: First Admin setup

1. Provisioning tạo `AuthAccount` với password ngẫu nhiên không dùng được,
   `TenantUser(pending_setup)` và role tenant `TENANT_ADMIN`.
2. Role nhận mọi permission có scope `TENANT` đang được seed trong public
   RBAC model.
3. Setup-link service revoke setup token chưa revoke của tenant, sinh secret
   32 byte, chỉ lưu SHA-256 hash và đặt hạn 24 giờ.
4. `/setup-account?token=…` kiểm tra password không rỗng và Confirm Password
   khớp trước khi gọi `POST /api/v1/setup/redeem`.
5. Backend kiểm tra token chưa dùng/revoke/hết hạn và First Admin còn
   `pending_setup`; một transaction consume token, cập nhật password hash,
   chuyển user sang `active` và revoke token sibling.
6. UI xóa token khỏi history URL sau thành công; token sai/hết hạn cùng hiển
   thị một trạng thái lỗi không tiết lộ identity.

## Acceptance criteria ưu tiên

### US-01 — Mời user trong giới hạn tenant

Với Tenant Admin có quyền quản lý user, khi tổng seat đã bằng `max_users` và
admin gửi invite mới, API trả `400 QUOTA_EXCEEDED` và không tạo bất kỳ bản ghi
user/invite nào. Sau khi revoke một invite đang chiếm seat, cùng request hợp
lệ phải tạo invite và trả `201`.

### US-02 — Tự đăng ký theo chính sách tenant

Với self-registration bật và whitelist `acme.com`, email ngoài domain trả
`400 DOMAIN_NOT_ALLOWED`; email thuộc domain tạo tài khoản theo trạng thái phụ
thuộc `require_approval`. Sau khi admin tắt self-registration, request hợp lệ
khác trả `403 SELF_REG_DISABLED` và không tạo user.

### US-03 — Hard delete có chuyển giao

Với source user sở hữu dữ liệu và target user `ACTIVE` cùng tenant, khi admin
xác nhận hard delete, hệ thống đổi toàn bộ owner sang target, ghi audit chuyển
giao và xóa source trong cùng transaction. Nếu target không hợp lệ, toàn bộ
thay đổi phải rollback.

Ba user story trên là acceptance criteria từ SRS và **chưa có test thực thi**
trong repository hiện tại.
