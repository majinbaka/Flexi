Technique 02 — Assumption Reversal

Ten load-bearing assumptions baked into the 3-tier design, filed as index cards. Flip a card to check its underside — one of them (#1) turned out to hold the whole session's real payload.

Most suspect, by the user's own read

User
  1. (a) a user belongs to exactly one tier
  2. (b) an Admin belongs to exactly one tenant
  3. (c) Permission = Role, with no surrounding context

Flagged as the likely origin of a forced refactor once Flexi grows into multi-tenant membership, partner portals, or enterprise accounts.

Decision — Direction 3 chosen: model SystemUser as a table separate from the tenant-scoped User table, to represent Super Admin cleanly.

Assumption #1, reversed

User

Tier is not a fixed permission set. It's just an operating zone — authority is granted independently through Role/Permission. A given SystemUser might only be a BillingOperator or TenantSupport; holding the Super Admin badge no longer implies holding every key.

That single reversal cascaded into six concrete design consequences:

Consequence 1 User

A spec line like if isSuperAdmin: bypass permission check is a dangerous hidden assumption. SystemUser should flow through ordinary RBAC (User → Role → Permission) — never a bypass.

Consequence 2 User

Distinguish Root (an emergency break-glass actor, outside RBAC entirely) from Super Admin (still ordinary RBAC). Two different concepts that keep getting merged.

Consequence 3 User

If the Permission catalog is shared across SYSTEM and TENANT, it needs a Permission.scope column plus a constraint blocking a TenantRole from ever being granted a SYSTEM permission (e.g. a Tenant Admin can't be handed tenant.delete).

Consequence 4 User

Impersonation (Super Admin logging in as a tenant user) needs to be designed in from day one via a JWT claim, impersonatedBy — instead of getting hacked in later through an X-Impersonate-User header.

Consequence 5 User

Once impersonation exists, audit logs need separate actorType/actorId alongside effectiveUserId/effectiveTenantId — not just the effective user.

Consequence 6 User

One email can legitimately be both a SystemUser (Platform Admin) and a TenantUser across several tenants. So identity/login should split out into its own AuthAccount, separate from SystemUser/TenantUser membership — avoiding duplicate logins per email.

Decision — Resolve gap #8 (AuthAccount vs. SystemUser vs. TenantUser) before the ERD is locked; it's the point most likely to force a large refactor later.
MVP decision — AuthAccount split out from the start. SystemUser and TenantUser are separate tables. One AuthAccount can only be one actor type (System xor Tenant); a TenantUser belongs to exactly one tenant. No workspace picker, actor switching, or multi-tenant membership at MVP.
Why — today's actors are only Platform Operator vs. Customer User. There's no real use case yet (MSP, agency, reseller, internal shared services) to justify the complexity of a multi-context JWT or actor switching.
Enforcement — the one-actor-per-account and one-tenant-per-TenantUser rules live at the service layer, not as hard DB unique constraints — so loosening the rule later only means changing code, not re-migrating the ERD.

Synthesis

Two separate findings from earlier in the sheet turn out to be the same mechanism, seen at two different layers.

§1 · Permission Ceiling

Admin → User: whatever role an Admin hands out, the system hard-limits it to the granter's own scope.

§2 · Permission.scope Guard

Assumption #1: a TenantRole can never be granted a SYSTEM-scoped permission — the catalog itself enforces the boundary.

=

One mechanism, two layers

Coach  "The permission ceiling" and "the Permission.scope guard" are the same rule: an actor can never grant authority beyond its own. Code it once, share it everywhere it applies.

Coach  That also means the ceiling UI built for Admin → User must extend to the Super Admin console when it assigns SYSTEM permissions — not stop at Admin → User.
