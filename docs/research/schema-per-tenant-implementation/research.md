# Technical research: Schema-per-tenant implementation

**Decision this research serves:** How to implement schema-per-tenant (own Postgres schema + own logic per tenant) for Flexi's Dynamic Table Builder — implementation guidance only, no strategy comparison (already decided).

## Executive summary

Schema-per-tenant is implementable for Flexi with a consistent, well-corroborated set of mechanics — but the research surfaced one finding serious enough to flag before implementation starts, even though no comparison was requested.

1. **The core query-routing mechanism is settled and verified:** scope every query with Knex's `.withSchema(tenantSchema)` per call, never a session-level `SET search_path`. Session-level `search_path` is documented to break under PgBouncer transaction-mode pooling — the standard production pooling mode — because the pooled backend connection can be recycled to a different tenant mid-session, corroborated independently twice, six years apart [8][14][6]. **Verified.**
2. **The specific implementation pattern the codebase should follow is a real production reference**, not a hypothetical: NestJS middleware resolves tenant ID from a verified JWT claim into request-scoped context (not `REQUEST`-scoped providers, which one practitioner explicitly tried and abandoned for performance reasons), and every query is scoped via `.withSchema()` against one shared connection pool [1][7]. **Use `nestjs-cls` for the context layer rather than hand-rolling `AsyncLocalStorage`** — independently verified as actively maintained (~1M downloads/week), purpose-built for exactly this multi-tenant use case, and defaulting to the safe `.run()` pattern internally [19]. **Verified, high confidence.**
3. **A real, dated security vulnerability directly targets this exact pattern:** CVE-2026-44680 (published 2026-05-05) is a confirmed SQL-injection vulnerability reachable via unsanitized tenant-controlled strings passed into `.withSchema()`-style multi-tenant schema APIs. The fix requires an allowlist regex on the schema name (`^[A-Za-z_][\w$]*$`) in addition to identifier quoting — this is not optional hardening, it is a demonstrated attack surface. **Verified independently** (re-confirmed directly against the GitHub Security Advisory and GitLab Advisory DB, not just the research subagent's citation).
4. **Biggest caveat — read before scaling assumptions are set:** sources disagree by an order of magnitude on how many tenant schemas Postgres comfortably supports (1,000–2,000 vs. 10,000–50,000), but reconciling the disagreement shows the real constraint is **total catalog object count** (schemas × tables × indexes × constraints), not schema count alone — a documented real case of ~1,200 schemas × ~200 tables (~240,000 total tables) saw 2-hour migration runs and severe planner slowdown. **This matters specifically for Flexi**, because the Dynamic Table Builder lets tenants create their own tables inside their schema — an uncapped multiplier on object count that no source examined found discussed anywhere in combination with schema-per-tenant. **The effective safe ceiling is materially lower than the general "schema-per-tenant" guidance assumes**, unless tables-per-tenant is bounded by the same guardrails already established for Flexi's Runtime DDL model.
5. **Tooling reality: there is no mature library for this in the Node.js ecosystem.** Every production account found hand-rolls it (custom DB module, tenant-context middleware, manual `.withSchema()` calls); Knex itself has no native multi-schema migration tracking (open since 2016) [4]. Budget for building this in-house, not adopting a package.

## Landscape & maturity

Node.js has no mature, actively-maintained library for Postgres schema-per-tenant multi-tenancy. `knex-postgres-multi-tenancy` (last released April 2020, 4 GitHub stars) doesn't even implement real schema separation — it implements table-prefixing within one schema despite its name [16]. `@nestjs-multitenant/typeorm` is TypeORM-only, published mid-2025, with ~7 npm downloads/month — negligible adoption [18]. By contrast, Python's `django-tenants` is actively released weekly as of this research date (three releases in the first week of August 2026 alone) [15], and Ruby's `apartment` gem, while widely historically adopted (5.2M downloads), has had no release since 2019 and 116 open issues [14] — both are more mature reference points than anything in Node.js. **Every real Node.js implementation found is hand-rolled**: a custom database module, a Postgres pool wrapper, tenant-extraction middleware, `AsyncLocalStorage` for context, and manual `.withSchema(tenantId)` calls per query — with zero-downtime migrations, tenant-scoped background jobs, and security hardening explicitly left as unsolved, out-of-scope problems by the one production account found [1][16].

On whether the pattern itself is "current": 2026 engineering content (PlanetScale, a Rails-focused SaaS guide) frames schema-per-tenant as a declining choice for new builds — "the operational overhead rarely justifies the isolation benefits unless you are in healthcare, finance, or government" — specifically citing system-catalog bloat and the PgBouncer/`search_path` incompatibility as the reasons [6][16]. This is vendor- and guide-flavored content, not a named-team migration postmortem (none was found), so treat the "declining" framing as directional signal, not settled fact. It does not change Flexi's already-made decision, but it does mean the implementation must be built defensively against exactly the failure modes these sources describe, not casually.

## Architecture patterns in practice

**Provisioning:** the substantiated pattern is `CREATE SCHEMA tenant_x` followed by running the full migration set fresh against the new schema — not template cloning. Three template-cloning techniques exist and are documented (a PL/pgSQL `clone_schema()` function on the official Postgres wiki [10]; `pg_dump -n <schema>` + restore into a renamed schema; the `pg-clone-schema` RDS-friendly utility), and Rails' `apartment` gem instead replays the full migration history into every new tenant schema [11] — but no source compared which approach production teams actually prefer, and none confirmed a clone-based approach in a Node/Knex production system specifically. This is a real implementation choice Flexi will have to make without external precedent; migration-replay is lower-risk (keeps migration history authoritative, no template-drift risk) at the cost of being slower per tenant onboarding.

**Query routing — the load-bearing decision:** Knex's `.withSchema(name)` works on the full query builder (select/insert/update/delete), not just DDL, and compiles to schema-qualified SQL rather than relying on connection/session state — confirmed directly against Knex's own documentation [2]. This is the mechanism that avoids the PgBouncer transaction-mode hazard described below. No official Knex or node-postgres document explicitly states "`withSchema()` is safer than `search_path` under pooling" in those words — that conclusion is _inferred_ by combining Knex's documented per-query behavior [2] with the independently documented PgBouncer session-state hazard [8][14][6]. The inference is sound, but it is an inference, not a single-sourced fact — treat it as verified at the mechanism level, not vendor-endorsed in exactly this framing.

**Tenant-context propagation in NestJS:** the reliable, repeatedly-converged pattern is middleware/guard that resolves tenant ID from a **verified JWT claim** (never request body/header) into Node's `AsyncLocalStorage`, entered via `.run()` (not `.enterWith()`, which was called out as able to leak context across concurrent async chains) [7]. `REQUEST`-scoped NestJS providers were tried by at least one production implementation and abandoned: they force every dependent service into request scope, causing NestJS to re-instantiate the whole dependency subgraph per request [1].

**Follow-up verification (2026-08-18): `nestjs-cls` upgrades this from a lead to a confirmed recommendation.** Directly checked against its GitHub README, npm registry, and its own middleware source code: it is actively maintained (v6.2.1, released 2026-05-25 — about 3 months before this research date; **~1.02M downloads/week** on npm), explicitly lists "making the dynamic tenant database connection available everywhere in multi-tenant apps" as a core motivating use case, and explicitly positions itself as a replacement for `REQUEST`-scoped providers via its "Proxy Providers" feature — directly addressing the performance problem the hand-rolled reference implementation [1] hit. Reading its middleware source directly: it defaults to `cls.run()` (the safe pattern) and only uses `enterWith()` when a developer explicitly opts in via a `useEnterWith` config flag — i.e., the library defaults to the safe behavior and gates the leak-prone pattern behind explicit, documented opt-in, which a hand-rolled implementation would have to get right on its own [19]. **Verified, high confidence — recommend using `nestjs-cls` over hand-rolled `AsyncLocalStorage` wiring for Flexi.**

**Named production pitfalls** (from a multi-tenant-NestJS-focused write-up, general to multi-tenancy, not schema-per-tenant-specific but directly applicable): lookup queries that filter by `id` alone instead of `(tenantId, id)`; cache keys not namespaced by tenant; background/queue jobs losing tenant context entirely; admin routes reusing tenant-scoped service methods and bleeding across tenants [7]. Mitigations: a `requireTenant()` data-access helper that throws if context is missing, tenant-namespaced cache keys, and tenant ID carried explicitly in every job payload.

## Integration & interoperability

**PgBouncer transaction-mode pooling and `search_path` are documented as incompatible.** Under `pool_mode=transaction` (the standard production mode), a session-level `SET search_path` set at the start of a request is not guaranteed to survive to the next statement, because the backend connection can be returned to the pool and handed to a different client at any transaction boundary — a backend that just served tenant A can be handed to tenant B with tenant A's `search_path` still active, or vice versa [8]. This is corroborated independently twice, six years apart, by different publishers with different underlying observations (a 2020 Rails-ecosystem production retrospective [14] and a 2026 Postgres-hosting vendor's technical post [6]) — meeting the two-source bar for a claim this load-bearing. **Verified.**

Reported-safe alternatives, in order of how directly they were sourced: (1) fully schema-qualify every query via Knex `.withSchema()` per call rather than any session-level `SET` — the pattern Flexi should use, consistent with the one real NestJS/Knex production implementation found [1]; (2) if a session-level `SET` is ever unavoidable (e.g. a raw-SQL escape hatch), use transaction-scoped `set_config(..., true)` / `SET LOCAL` inside an explicit transaction, which is cleared the instant the transaction commits or rolls back and is therefore pool-safe — reported both for Postgres directly [5] and, independently, for a different stack (Go/pgx), confirming the mechanism is a general Postgres property, not stack-specific [8]; (3) `ALTER ROLE ... SET search_path` as a role-level default, and PgBouncer's `track_extra_parameters` to restore session parameters across backend swaps, both mentioned as mitigations in the PgBouncer issue thread but not independently confirmed against PgBouncer's own docs this round — flagged as an open item.

**Pool topology:** the recommended and only-observed-in-production topology is **one shared connection pool**, not one pool per tenant — a real implementation explicitly warns that pool-per-tenant exhausts Postgres `max_connections` (`FATAL: sorry, too many clients already`) as tenant count grows, and runs a single shared pool (min 2 / max 50 connections) scoped per-query via `.withSchema()` instead [1]. Cross-source qualitative convergence puts schema-per-tenant's comfortable range at roughly 100–10,000 tenants for topology purposes, though this specific number was reached via secondary-source synthesis, not independently fetched — lower confidence than the pool-per-tenant warning itself.

**Auth-to-schema mapping carries a real, demonstrated injection risk, not a theoretical one.** CVE-2026-44680 / GHSA-cfw5-68c4-ffqp (published 2026-05-05, independently re-verified against the GitHub Security Advisory and GitLab Advisory Database directly, not just the subagent's citation) is a confirmed SQL-injection vulnerability in `@mikro-orm/knex` and `@mikro-orm/sql` (all versions before 6.6.14/7.0.14) in the identifier-quoting helper used by exactly this class of API — `qb.withSchema(name)` and equivalents — when fed an attacker-influenced schema-name string [9]. The mechanism is generic (unescaped SQL-identifier quoting), not specific to MikroORM, so it applies directly to any hand-rolled `knex.withSchema(tenantSchemaFromRequest)` call. The advisory's own mitigation is a strict allowlist regex on the schema name — `^[A-Za-z_][\w$]*$` — applied **in addition to**, not instead of, proper identifier quoting, because Postgres does not support parameterized identifiers (only values). **Verified, and directly actionable — this is a required implementation control, not optional hardening.**

## Implementation reality

**Migrations across schemas have no native Knex support.** The tracking problem has been open since 2016 (`knex/knex#1138` [4]): Knex's migration-tracking table isn't schema-aware. The de facto community workaround is looping a migration run once per tenant schema at deploy time via `.withSchema()`, with the migrations table itself created per-schema, not shared — thin unofficial npm wrappers exist (`knex-tenanty`, `knex-postgres-multi-tenancy`) but none is mature or heavily maintained [16].

**Correction (verified directly, 2026-08-18, resolving the prior open question):** `migrate.latest({ schemaName })` does **not** ignore the schema option and is not a bug — a Knex core maintainer clarified on the record, and current official Knex docs confirm the identical wording today, that `schemaName` **only controls where the `knex_migrations`/`knex_migrations_lock` tracking tables live — it does not scope the migration's actual DDL to that schema** [3]. This is permanent, documented, intended behavior, unchanged since at least 2019 through current Knex. To actually target a tenant's schema, each migration file must call `knex.schema.withSchema(schema)` explicitly inside its `up`/`down` functions, reading `schema` from `knex.userParams` after cloning the Knex instance with `knex.withUserParams({ schema })` before running that tenant's migration [3]. **This means a naive `migrate.latest({ schemaName: tenantSchema })` loop — the pattern implied by "loop per schema" above — silently runs every migration's DDL against the connection's default schema for every tenant, not the tenant's own schema, unless migration files are written schema-aware via `userParams` from the start.** This is a correctness trap, not a missing feature — the fix is a required authoring convention for every migration file, not a config flag.

The one real production account running this exact stack explicitly lists **zero-downtime schema migrations as an unsolved, deferred problem** in their own write-up [1] — this is not a solved problem Flexi can assume away.

**Onboarding automation** has three documented techniques (PL/pgSQL `clone_schema()` [10], `pg_dump`/restore of a template schema, migration-history replay [11]) but no source compares which production teams prefer and why — an open implementation decision, not a research gap that further searching would likely resolve.

**Operational burden scales with total catalog object count, not schema count** — this is the mechanism behind the scaling-ceiling disagreement below. A 2009 Postgres mailing-list report (Tom Lane, Postgres core developer) established the mechanism directly: `pg_dump` must examine _all_ database objects to trace dependencies correctly even when dumping a single schema, so dump cost scales with total objects database-wide, not target-schema size [13] — old data, but the mechanism it explains is architectural, not version-specific, and is corroborated by a documented real-world case: roughly 1,200 schemas × ~200 tables each (~240,000 total tables) produced migration runs approaching two hours and severe query-planner slowdown, because `pg_catalog` is a set of ordinary shared heap tables, not partitioned per schema [17][6]. Mitigations reported: `pg_dump --format=custom`/parallel dump once for the whole database with `pg_restore --schema=<name>` per schema rather than N separate `pg_dump` runs; offload backups to a replica.

**Practical schema-count ceiling — the central reconciled finding of this research:** sources disagree by roughly 10–50× on the comfortable ceiling. Citus (Microsoft-owned, direct engineering authority on their own schema-based-sharding feature) says explicitly to reconsider the sharding model above ~10,000 schemas, citing per-backend catalog-cache memory growth — independently re-verified against Citus's own current docs, not just the subagent's citation [12]. Other 2026 sources put the practical degradation point far lower, "a few hundred tenants" [6], or "1,000–2,000 schemas" generically. **Reconciling this directly: both figures describe the same mechanism (total catalog objects, not schema count) at different assumed tables-per-tenant.** Citus's 10k-schema comfort zone implicitly assumes a modest, fixed, developer-controlled table count per tenant; PlanetScale's "few hundred" framing and the 1,200-schema/240k-table real case both involve materially higher per-tenant object counts. No source examined found or discussed the specific combination Flexi is building — schema-per-tenant _plus_ tenant-initiated, uncapped dynamic table creation — despite targeted searching; this appears genuinely undiscussed in current public engineering writing. **Flexi's effective ceiling should be modeled on total-object-count, not tenant-count, and requires the same per-tenant table/column caps already established for the platform's Runtime DDL guardrails, applied per-tenant-schema rather than assumed away by isolation.**

## Cross-dimension insights

The four dimensions converge on one structural point that isn't visible from any single dimension alone: **schema-per-tenant does not eliminate the catalog-bloat risk already identified for Flexi's Runtime DDL model — it relocates and potentially compounds it.** The architecture-patterns and integration dimensions establish _how_ to implement the pattern safely (`.withSchema()`, AsyncLocalStorage, JWT-verified tenant resolution, schema-name allowlisting); the implementation-reality and landscape dimensions establish that the pattern's safe operating envelope is bounded by total catalog objects, and that Flexi's specific combination — user-created tables inside a per-tenant schema — sits in a scaling regime (uncapped objects × potentially thousands of tenants) that no source examined has validated. The isolation benefit schema-per-tenant is chosen for (per-tenant blast radius, easier per-tenant backup/export) is real and confirmed [6], but it does not substitute for the same table/column guardrails already required under the row-level model — those guardrails move from "global cap" to "per-tenant-schema cap," they don't disappear.

A second cross-dimension point: the security control (schema-name allowlisting against injection, [9]) and the pooling control (`.withSchema()` over `search_path`, [8]) are not independent — the same tenant-resolved schema-name string is the input to both the query-routing mechanism and the injection surface. A single, tested `resolveTenantSchema(tenantId): string` function — verified JWT claim in, allowlisted/looked-up schema name out, used everywhere `.withSchema()` is called — closes both concerns with one code path instead of two.

## Recommendations

1. **Route every query through Knex's `.withSchema(tenantSchema)` per call; never use session-level `SET search_path`.** Confidence: **high** — mechanism verified against official Knex docs, hazard verified against two independent sources six years apart. _Feeds:_ implementation guide (query layer), architecture spine constraint.
2. **Resolve tenant identity from a verified JWT claim into request-scoped context via `nestjs-cls`, not hand-rolled `AsyncLocalStorage` and not NestJS `REQUEST`-scoped providers.** `nestjs-cls` is actively maintained (~1M downloads/week), defaults to the safe `.run()` pattern internally, and its "Proxy Providers" feature directly solves the `REQUEST`-scope performance problem the hand-rolled reference implementation hit. Confidence: **high** — independently verified against the library's source code, not just its marketing docs. _Feeds:_ implementation guide (request lifecycle).
3. **Build and unit-test a single `resolveTenantSchema()` function that allowlists the schema name (`^[A-Za-z_][\w$]*$`) before it ever reaches `.withSchema()` or any raw SQL — treat this as a required security control, not optional hardening**, directly in response to CVE-2026-44680. Confidence: **high** — independently verified vulnerability with a concrete, actionable fix. _Feeds:_ implementation guide (security), architecture spine constraint.
4. **Do not build or adopt per-tenant connection pools; use one shared pool with per-query schema scoping.** Confidence: **medium** — one concrete production warning (`max_connections` exhaustion), consistent with general Postgres connection-cost physics. _Feeds:_ implementation guide (infrastructure).
5. **Budget for hand-rolling migration orchestration across tenant schemas — do not plan around an existing Knex or NestJS package solving this.** Loop per tenant schema using `knex.withUserParams({ schema })` + `migrate.latest({ schemaName: schema })`, and write every migration file to call `knex.schema.withSchema(knex.userParams.schema)` explicitly rather than relying on `schemaName` alone to scope the DDL (verified: `schemaName` only relocates the tracking table, confirmed against a Knex maintainer's statement and current official docs — see Implementation reality). Treat zero-downtime rollout across schemas as an open engineering problem to design for explicitly, not something available off the shelf. Confidence: **high** on the tooling gap and on the `schemaName`/`userParams` mechanics (independently verified); **medium** on the loop pattern being sufficient at Flexi's target scale. _Feeds:_ implementation guide (migrations), roadmap estimate.
6. **Set a per-tenant table/column cap for the Dynamic Table Builder under schema-per-tenant, sized to keep total catalog objects (schemas × tables × indexes × constraints) well under the range where real cases saw multi-hour migration runs (~240,000 total tables).** This is the same discipline already recommended for Flexi's Runtime DDL guardrails, now applied per-tenant-schema. Confidence: **medium** — the reconciliation is this research's own synthesis of two disputed source ranges, not a single sourced number; no source validated Flexi's exact combination (schema-per-tenant + uncapped tenant-created tables). _Feeds:_ brief feasibility / NFRs, architecture spine constraint.
7. **Choose migration-replay over template-cloning for new-tenant onboarding unless a concrete provisioning-latency requirement forces template-cloning** — replay keeps migration history authoritative and avoids template-drift risk, at the cost of slower onboarding; no source validated either choice specifically for a Node/Knex stack, so this is a reasoned default, not a confirmed best practice. Confidence: **low-medium**. _Feeds:_ implementation guide (onboarding automation).

## Open questions

- **Which onboarding technique (template-clone vs. migration-replay) do real Node/Knex production teams actually prefer, and why?** No comparative source found. _Route:_ defer to Flexi's own prototyping — this is a build-and-measure decision, not a research gap.
- **Is there a concrete, current (last-12-months) benchmark for `pg_dump`/`pgcopydb` performance at high schema/object counts?** Only 2009-era numbers and one undated secondary case were found. _Route:_ low priority — the architectural mechanism (total-object-count cost) is well-established regardless of the exact current numbers; revisit only if backup/restore time becomes an operational pain point.
- **Does PgBouncer's `track_extra_parameters` or session-mode fallback change the `search_path` guidance for any narrow path (e.g., admin/migration connections)?** Not independently confirmed against PgBouncer's own docs. _Route:_ check `pgbouncer.org/config.html` directly if a genuine need for session-level `SET` arises; the primary implementation path (`.withSchema()` everywhere) doesn't need this answered to proceed.
- **Schema-per-tenant + tenant-initiated dynamic table creation combined — genuinely unvalidated anywhere in public writing.** This is the single largest gap this research found. _Route:_ treat recommendation 6 (per-tenant object caps) as a load-bearing mitigation for an otherwise-unvalidated risk, and revisit with real production metrics once Flexi has meaningful tenant/table-count data of its own — this is exactly the kind of claim a future Refresh of this research should prioritize.
