Executive summary

The import argues for Runtime Physical DDL (real CREATE TABLE/ALTER TABLE per user-defined table/field, native Postgres types) as the storage strategy for a row-level multi-tenant, REST-only, Postgres-backed Dynamic Table Builder — the same approach used by Baserow, NocoDB, Directus, and Retool DB — over JSONB-hybrid (Xano-style), EAV, or an in-memory grid engine (Airtable-style).

Three findings drive that recommendation, each spot-checked against independent Postgres/Prisma/Knex documentation:

  1. Postgres's ACCESS EXCLUSIVE lock on ALTER TABLE is real and does cascade-block a busy table — an enforced lock_timeout and async DDL queue are a genuine safety requirement. verified
  2. ADD COLUMN … DEFAULT has been metadata-only (O(1)) since Postgres 11 — additive schema changes are cheap by default. verified
  3. Prisma's compile-time schema model is a hard architectural mismatch for user-created runtime tables — the case for a separate Knex.js-based dynamic layer is sound. verified
Biggest caveat: the import carries zero external citations, publisher names, or dates for any claim — including every numeric guardrail (row limits, rate limits, page sizes) and all four named postmortems. Treat those as plausible illustrative figures, not confirmed facts. The architectural mechanics check out against real documentation; the specific numbers attached to them do not.

Two pack dimensions the import doesn't cover: integration & interoperability (auth patterns, protocols beyond "REST-only") and ecosystem health (release cadence / maintenance risk of the platforms and libraries named). See Open Questions.

Baserow's placement in the Runtime-DDL group checks out independently: it's a Django + PostgreSQL app where every user-defined table is a real Django model backed by an actual Postgres table via TableHandler and Django migrations [2] verified. NocoDB and Directus's descriptions are consistent with public positioning but weren't independently re-verified this pass — spot-check budget went to the mechanisms Flexi would actually build against.

Implication for Flexi: in a tenant_id-partitioned shared Postgres database, Runtime DDL requires every user-created physical table to carry a tenant_id column, paying off via a composite B-Tree on (tenant_id, …). JSONB-hybrid trades that performance for eliminating DDL-lock risk outright — a real trade, not a strictly dominant option either way.

Architecture patterns in practice

Scale trade-offs

Runtime DDL's scale risk is concrete and independently groundable: Postgres tracks structure in system catalogs (pg_class, pg_attribute, pg_index) and per-connection relcache; a very large number of physical tables inflates both, and relcache-invalidation messages broadcast to all connections on DDL churn. The import's threshold — split the model above roughly 20,000 dynamic tables system-wide — is a reasonable heuristic but unsourced; treat it as a starting guess to load-test, not a validated ceiling. unverified threshold

JSONB/Hybrid's cost is the mirror image: large JSONB values are TOASTed, and updating even one key inside a document rewrites the whole stored value — genuine write amplification, standard Postgres behavior.

Indexing for user-defined fields

  • Auto-indexed: primary key + tenant_id; foreign keys / relational link fields; a standard (tenant_id, created_at) composite for default pagination.
  • Opt-in (user marks a field "Filterable"/"Searchable"): (tenant_id, field) B-Tree for standard filters; GIN … gin_trgm_ops for fuzzy/LIKE '%x%' text search; (tenant_id, (data->>'key')) expression or jsonb_path_ops GIN for JSONB paths.
  • Leading-column rule: every index carries tenant_id as the leading column so a query only walks the current tenant's branch — never a global scan.

pg_trgm + GIN for fuzzy LIKE search is standard, documented Postgres behavior [5] verified.

Runtime DDL safety

This is the import's strongest, most independently confirmable section:

  • ALTER TABLE takes ACCESS EXCLUSIVE, blocking all reads/writes and queuing behind (and blocking) other statements [4] verified.
  • SET lock_timeout = '2s' before DDL — a blocked ALTER fails fast instead of starving the connection pool.
  • ADD COLUMN … DEFAULT <constant> has been metadata-only since Postgres 11 [3] verified — a volatile default still forces a full rewrite (a caveat the import omits).
  • The 4-step online column-type-change pattern (new column → dual write → batch backfill → cutover/drop) is the standard industry "expand/contract" migration pattern, described correctly though not named as such.
  • Wrapping physical DDL + metadata updates in one SQL transaction, and moving DDL off the request/response path into a Redis-backed queue (BullMQ), are both standard, low-risk recommendations.

Implementation reality

Operational guardrails

The import proposes concrete ceilings — 100,000 rows/tenant table, 10–20 req/s/tenant, 100 columns/table, page size 50/100, batch limit 50, 2 MB body-parser limit, statement_timeout = '5s' — framed as consistent with Airtable/NocoDB/Baserow/Teable tiers. None of these numbers carry a source in the import; this pass did not independently re-verify vendor tier pages. unverified Treat as a starting proposal, not a benchmarked figure.

Query / CRUD layer

Prisma manages a fixed, compile-time schema and can't represent runtime-created tables without workarounds [6] verified · medium confidence. Knex.js is recommended as the dynamic query/DDL layer because it exposes both a query builder and a schema builder (knex.schema.alterTable(...)) against Postgres from Node.js [7] verified. Kysely and raw pg/Slonik are reasonably characterized as harder-to-use alternatives, not independently re-checked here.

For N+1 avoidance on linked-record REST responses: server-side json_agg/json_build_object aggregation in one query, or a DataLoader-style batched WHERE id IN (...) — both standard, sound techniques. Metadata caching (schema:{tenant_id}:{table_id} in Redis, invalidated on any DDL) is a reasonable complement, not independently checked.

Cross-dimension insights

The report's synthesis — Runtime DDL for core tables + tenant-id-leading composite indexes + a Knex layer separated from Prisma + async DDL with short lock_timeout + strict guardrails — holds together only if the guardrail numbers are validated against Flexi's real workload, because the whole safety story depends on bounding table count and row count per tenant. The verified mechanics explain why each guardrail exists; the guardrails themselves are the one part this pass could not confirm as more than a plausible starting point.

Recommendations

  1. Adopt Runtime Physical DDL as the default storage model, with mandatory tenant_id on every dynamic table and as the leading index column. medium confidence — mechanism verified, scale thresholds not. Feeds: candidate paradigm for the module's architecture spine.
  2. Enforce lock_timeout before every runtime DDL statement; run DDL through an async queue (e.g. BullMQ) outside the request/response cycle. high confidence. Feeds: architecture constraint (operational).
  3. Build the dynamic CRUD/DDL layer on Knex.js, separate from Prisma; use Prisma only for Flexi's fixed metadata tables. high confidence. Feeds: architecture spine, roadmap estimate.
  4. Re-derive numeric guardrails from Flexi's own tenant profile before adopting the import's figures, which have no traceable source. low confidence as stated. Feeds: brief feasibility / NFRs.
  5. Use server-side json_agg for linked-record REST responses to avoid N+1 — a well-established pattern independent of this report. high confidence. Feeds: architecture spine (API layer pattern).
